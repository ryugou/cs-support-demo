# 監査ログが poisoned になったインスタンスの切り離し

| 項目    | 内容 |
| ----- | ---- |
| 目的    | 監査ログ（`WormAuditLog`）が poisoned になったインスタンスが、正常と報告し続けて残る問題を解消する。あわせて、不完全な最終行が残った場合の復旧手順を定める（Issue #62） |
| 読者    | 実装者、レビュアー、障害対応を行う運用者 |
| 正本の範囲 | poisoned になったプロセスの振る舞い（ヘルス応答と終了）、復旧手順の判断基準 |
| 関連文書  | [`../../runbooks/`](../../runbooks/)（復旧手順の置き場所）、`server/src/harness/audit.rs`（ハッシュ連鎖と poisoned の定義） |

## 1. 採用する設計

監査ログが poisoned になったプロセスは、次の 2 つを行う。

1. **ヘルス応答を 503 にする**: `/livez` と `/healthz` は、そのプロセスが持つ監査ログのいずれかが poisoned なら 503 を返す。
2. **自分で終了する**: 受付済みのリクエストの処理を終えてから、0 以外の終了コードでプロセスを終了する。

poisoned はプロセス内の状態で、同じプロセスのままでは回復しない。再起動すると起動時の連鎖検証（`verify_chain`）が走り、ファイルが健全なら追記を再開できる。したがって、必要な処置は入れ替えではなく再起動である。

自分で終了する方式にする理由: 実行基盤の設定（ヘルスチェックの監視設定）に依存せずに再起動が起きる。Cloud Run でも、VM 上のコンテナ（再起動ポリシーつき）でも同じ挙動になる。ヘルス応答の 503 は、外部の監視から状態を観測するために残す。

監査の完全性を可用性より優先する方針（poisoned になったら追記を拒否する）は変更しない。

## 2. 型とインターフェース

### 2.1 `WormAuditLog`（`server/src/harness/audit.rs`）

```rust
impl WormAuditLog {
    /// ハッシュ連鎖の状態が poisoned かどうか。
    pub fn is_poisoned(&self) -> bool;
}
```

- 内部の状態を保護する Mutex が Rust の意味で poisoned（保持中の panic）だった場合も `true` を返す（追記できない点で同じ扱いにする）。
- 読み取りだけを行い、状態を変えない。

### 2.2 致命状態の通知

監査ログが poisoned に遷移したことを、サーバの起動処理へ伝える手段を追加する。

- `WormAuditLog` は、poisoned に遷移した時点で 1 回だけ通知を発行する（`tokio::sync::Notify` または `watch` チャネル。既存の依存で実現できるものを使う）。
- 通知の受け手は、プロセスの起動処理（`server/src/main.rs`、`server/src/bin/homesec_advisor.rs`）である。受け取ったら §3.2 の終了処理を始める。
- `WormAuditLog` 自身はプロセスを終了させない（ライブラリの中で `std::process::exit` を呼ばない）。

### 2.3 ヘルスルータ（`server/src/health.rs`）

`health_router` は、監視対象の監査ログを 0 個以上受け取る。

- 0 個の場合（LINE アダプタ）は、現行どおり常に 200 を返す。
- 1 個以上の場合、いずれかが `is_poisoned()` なら 503、すべて健全なら 200 を返す。
- 503 の応答本文は固定の短い文字列にする。ファイルパスやエラーの詳細を含めない（認証なしで到達できるため）。

各プロセスが渡す監査ログ:

| プロセス | 渡す監査ログ |
| --- | --- |
| `cs-support-mcp`（`main.rs`） | Harness の監査ログ |
| `homesec_advisor` | Harness の監査ログと、CS 連携用の監査ログ（`support_audit_log_path`）の両方 |
| `line_adapter` | なし |

## 3. 振る舞い

### 3.1 poisoned への遷移

`WormAuditLog::append` が耐久化に失敗して poisoned に遷移する条件と、その後の追記を拒否する挙動は変更しない。追加するのは通知の発行だけである。

### 3.2 終了処理

起動処理は、通知を受け取ったら次を行う。

1. `tracing::error!` を 1 行出す。どの監査ログ（パス）が poisoned になったか、プロセスを終了すること、再起動後に起動時検証が失敗した場合の参照先（§5 の runbook のパス）を含める。
2. 新しい接続の受付を止め、受付済みのリクエストの完了を待つ（graceful shutdown）。待つ時間に上限を設け、設定値として持つ（既定 30 秒）。上限を超えたら残りを打ち切る。
3. 0 以外の終了コードでプロセスを終了する。

TLS で待ち受ける経路（`axum_server`）と、平文で待ち受ける経路（`axum::serve`）の両方に適用する。

通知を受け取るまでは、起動処理と待ち受けの挙動を現行から変えない。

### 3.3 再起動後

| 再起動後の状態 | 挙動 |
| --- | --- |
| ファイルが健全（一過性の fsync 失敗で、行は書かれていないか完全に書かれている） | 起動時検証が通り、通常どおり動く |
| 不完全な最終行が残っている | 起動時検証が失敗し、起動しない（現行どおり）。§5 の runbook で復旧する |
| 保存先が継続して書き込めない | 起動 → 最初の追記で poisoned → 終了、を繰り返す。再起動の間隔は実行基盤の制御に従う。この間のリクエストは失敗する（現行でも poisoned のインスタンスは全件失敗するため、悪化しない） |

## 4. 不変条件

- poisoned になったプロセスは、監査ログへ追記しない（現行どおり）。
- ハッシュ連鎖が壊れたファイルを、プロセスが自動で修復・切り詰め・作り直すことはない。
- ヘルス応答は認証なしで到達できる。応答に内部情報を含めない。
- 監査ログを持たないプロセス（LINE アダプタ）の挙動は変わらない。

## 5. 復旧手順（runbook）

`docs/runbooks/audit-log-recovery.md` を新規に作成する。内容は次の判断基準に従う。

### 5.1 判断基準

1. **対象は最終行だけである**: 最終行より前の行で起動時検証が失敗する場合は、改竄または破損の疑いとして扱い、ファイルに手を加えない。runbook はこの場合の手順を定めず、調査へ回すことだけを書く。
2. **不完全な最終行は取り除いてよい**: 最終行が改行で終わっていない、または JSON として読めない場合に限る。理由: 不完全な行は書き込みの途中で失敗した断片で、ハッシュ連鎖に組み込まれていない。取り除いた後のファイルは、最後に成功した追記の時点の正しい連鎖になる。
3. **完全な最終行は取り除かない**: 最終行が JSON として読め、連鎖の検証だけが失敗する場合は 1 に当たる。
4. **元のファイルを残す**: 取り除く前に、元のファイルを別名で同じ保存先へ保存する。上書きしない。
5. **取り除いた事実を記録する**: 取り除いたバイト列、その長さ、作業日時、作業者、判断の根拠を、障害の記録（Issue）に残す。監査ログへ自動で追記する仕組みは作らない。
6. **書き戻しは同時更新を検出する方法で行う**: 作業中に別のプロセスが書き込んでいた場合に、上書きで失わない。

### 5.2 runbook に書くこと

- 症状の見分け方（起動時のエラー文のどの文言が、どのケースに当たるか。`server/src/harness/audit.rs` の実際のエラー文を引用する）
- 作業前の確認（対象のサービスが起動に失敗していること、監査ログの保存先の特定方法）
- 手順（取得、最終行の確認、元ファイルの保存、取り除き、書き戻し、再起動、起動の確認）。コマンドは 1 行ずつ、そのまま実行できる形で書く。値が環境ごとに異なる箇所は、何を入れるかと調べ方を書く
- 対象が複数あること（`homesec_advisor` は監査ログを 2 つ持つ）
- やってはいけないこと（完全な行の削除、ファイルの作り直し、元ファイルを残さない作業）

保存先の実際のバケット名やマウント設定は、リポジトリから読み取れる範囲（設定ファイルのパス）で書き、読み取れない値は調べ方を書く。推測で値を書かない。

## 6. テスト

| 対象 | 固定する内容 |
| --- | --- |
| `WormAuditLog::is_poisoned` | 健全なときは `false`。耐久化の失敗で poisoned に遷移した後は `true`（既存の、実際の書き込み失敗を起こすテストと同じ方法で遷移させる） |
| 通知 | poisoned への遷移で通知が 1 回発行される。健全な追記では発行されない。既に poisoned の状態で追記を拒否したときに再度発行されない |
| ヘルスルータ | 監査ログ 0 個は常に 200。健全な監査ログでは 200。いずれか 1 つが poisoned なら `/livez` と `/healthz` の両方が 503。503 の本文にパスが含まれない |
| 終了処理 | 通知を受けると終了処理が始まり、受付済みのリクエストが完了してから終了する。終了コードを決める部分と、待ち時間の上限の適用を、プロセスを実際に終了させずに検証できる形に切り出す |
| 既存の挙動 | 監査ログの既存テスト、ヘルスの既存テストが通る（ヘルスの既存テストは、引数の追加に合わせた最小の修正だけを行う） |

## 8. 対象外

- 実行基盤のヘルスチェック設定（Cloud Run の liveness probe など）の変更。自分で終了する方式により、設定を変えなくても再起動が起きる。
- 監査ログの保存方式の変更、不完全な行を取り除くツールの実装。
