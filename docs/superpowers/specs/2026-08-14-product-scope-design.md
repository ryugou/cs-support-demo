# 取扱製品スコープの前提化

| 項目 | 内容 |
| --- | --- |
| 目的 | 「当社が取り扱う製品以外には答えない」を、会話全体（判定・材料・聞き返し・回答・最終ゲート）の前提として定める |
| 読者 | 実装エージェント、レビュー担当 |
| 正本の範囲 | 取扱スコープの正本と取得方法、5 つの注入点の仕様、取扱外応答の文言、適用範囲 |
| 関連文書 | `2026-08-11-answer-api-line-adapter-design.md`（/api/reply 契約）、`2026-08-12-conversation-flow-v11-design.md`（会話フロー）、GitHub Issue #28 |

## 1. 採用する設計

取扱スコープは「型番を検出して弾くフィルタ」ではなく、**すべての生成・材料選別に最初から注入される前提**とする。マニュアルコーパスは全 Alarm.com 製品を含んでよい（共通内容が取扱製品にも有用なため）が、**応答のスタンスは常に取扱製品のみ**であり、聞き返しの選択肢にも取扱外の製品種別を出さない。

スコープの正本は**製品マスタ（vegapunk の Product ノード）**。`server/data/urtect/products.json` は seed 入力記録で、本件で次の 7 型番に更新する:

`ADC-V523` / `ADC-V523X` / `ADC-V724` / `ADC-V724X` / `ADC-VC729P` / `ADC-VC727P` / `ADC-VC827P`

（name = model、aliases は空。反映は CI デプロイ後に `ingest-products` job を実行）

コードへの型番ハードコードを禁止する。

## 2. 取扱一覧の取得とキャッシュ

- `/api/reply` の処理系は Product ノード一覧（**model のみ**。allowlist は `model` 属性だけで構築し `name` は併合しない）を vegapunk から取得し、プロセス内に TTL 10 分でキャッシュする
- 取得失敗時: キャッシュがあれば期限切れでも使う（stale 許容）。キャッシュが一度も無い状態で取得に失敗した場合は 503（`upstream_unavailable`）。vegapunk 不達時は検索も成立しないため、既存のエラー意味論と一致する
- 一覧の表示文字列（「ADC-V523/V523X、ADC-V724/V724X、…」）はマスタからコードで組み立てる

## 3. 注入点（5 つ）

### 3.1 質問側ゲート（二段構成: 決定論フロア + LLM 解釈）

顧客入力は型番の正確な表記を期待できない（小文字・ハイフン欠落・`ADC-` 省略・俗称・「ドアベル」のようなカテゴリ言及）。そのため質問側は二段で判定する。**解釈は LLM、判定はコード**（時間帯受付と同じ規律）。

**一段目（決定論フロア、従来どおり）**: 下記の正規形検出で取扱外型番が確定した場合は、LLM を使わず evaluate 前に短絡して取扱外定型応答（第 4 節）を返す。

**二段目（LLM 解釈 + コード判定）**: 一段目で未検出の場合、evaluate 内で毎ターン実行している既存の signal 抽出 LLM 呼び出しの出力スキーマを拡張し（**追加 LLM 呼び出しなし**）、製品参照を構造化抽出する:

- 抽出スキーマ: `product_references: [{ surface: string, resolution: "matched" | "ambiguous" | "foreign", matched_model: string | null }]`。プロンプトに取扱カタログ（第 2 節の一覧）を注入し、「製品への言及と思われる表層（型番・略記・俗称・カテゴリ的言及）を抽出し、カタログ製品でありうるなら matched / 曖昧なら ambiguous、**カタログのどれでもあり得ない別製品への言及と確信できる場合のみ foreign**」と指示する
- コード判定: `foreign` の参照について、(a) `surface` が正規化後のメッセージ中に実在すること（幻覚ガード）、(b) `surface` が trim 後 2 文字以上であること、(c) `surface` が trim 後 64 文字以下かつ制御文字（Cc / Cf / Zl / Zp・ゼロ幅を含む）を含まないこと（反射安全性。定型応答・ログへそのまま載せても安全な値であることの検証）、(d) `surface` と `matched_model` のどちらも決定論の allowlist 上で取扱内製品を指していないこと（LLM が製品マスタと矛盾する分類を返した場合への veto。ADC- 接頭辞を欠く型番断片もサフィックス一致で照合する）を検証したうえで、取扱外定型応答を返す（evaluate の結果は使わず破棄。下書きが生成済みでもコストとして受容し、応答には使わない）
- 断片のサフィックス一致には**最小長 3 文字**を課す（`MIN_FRAGMENT_VETO_CHARS = 3`）。「24」のような 2 文字断片は実在型番の末尾と偶然一致しても veto しない。閾値を下げると偶然一致の veto が増えて二段目ゲートの実効性が下がり、0 に近づくと空文字が全型番のサフィックスとなりゲートが無効化に向かうため、この定数は仕様である（実装バグではない）
- **Accepted Risk（2026-08-16 裁定）**: サフィックス一致の厳格化により、接頭辞側だけの断片（「VC729」= ADC-VC729P の末尾を欠く形、「V72」等）は veto されない。LLM が foreign と誤分類した場合、取扱内製品の顧客に取扱外応答を返す経路が理論上残る。発火には誤分類が前提で、除外 signal は次ターンで復元され会話は回復可能だが、顧客との 1 往復が失われる。緩い contains 照合へ戻すと逆に真の foreign の偽 veto が増えるため、この側を受容する
- `matched` / `ambiguous` / 参照なしは通常フロー（曖昧さは聞き返しがカタログから選ばせることで収束する）
- 抽出の失敗・parse 不能時は二段目をスキップし通常フローへ（一段目のフロアと応答側ゲート 3.5 が防衛線として残る）
- `EvaluationOutcome` への `product_references` の追加は加算であり、MCP `evaluate_answerability` には新フィールドが増えるのみ（既存フィールドの意味は不変。MCP 側でこの判定は行わない）

**二段目確定時の case 正本の遷移**: `evaluate()` は二段目判定より前に完了しており、対象 case へ signal 累積・`last_decision`（`allowed`/`escalate`）・`last_kr_id`・`last_evidence_keys`・`last_evidence_kind` を既に書き込んでいる。二段目が foreign と確定すると、顧客へ実際に返るのは第 4 節の取扱外定型応答であり、case の正本をこの事実に一致させる。専用の read-merge-write 1 回（`Harness::demote_case_to_out_of_scope`）で、既存属性（`question` を含む）を保持したまま `last_decision` を `out_of_scope_product` へ上書きし、`last_kr_id` / `last_evidence_keys` / `last_evidence_kind` を空文字へ消去する。今ターンに新規追加された signal は HAS_SIGNAL 辺として既に vegapunk へ書き込み済みだが、vegapunk 側に辺の削除 API が無いため物理削除はしない。代わりに同じ書き込みで case 属性 `excluded_signals`（CSV）へ追記し、以降の `evaluate()` が累積 signal を復元する際にこの集合を差し引くことで、破棄したターンの signal を累積へ反映させない。**この除外は永久ではない。** 除外した signal が後続ターンで顧客から改めて言及され今ターンの抽出結果に再度現れた場合は、`excluded_signals` から取り除いたうえで通常どおり累積へ反映する（除外を永久にすると、取扱外ターンで一度でも言及された hazard signal がその後のターンで正当に再観測されても `hazard_signal_count` に数えられず、エスカレーション判定が fail-open する）。

**一段目の正規形検出（決定論）**:

- 顧客メッセージから型番トークンを抽出する。正規化: NFKC（全角英数を半角へ）+ Unicode ハイフン類（U+2010〜U+2015・U+2212 数学マイナス記号・全角ハイフンマイナス U+FF0D）を ASCII `-` へ変換 + U+00AD SOFT HYPHEN を除去してから、正規表現 `(?i)ADC-[A-Z0-9][A-Z0-9-]*`（全面 case-insensitive・貪欲）でマッチし、大文字化して比較する
- **Accepted Risk（2026-08-14 裁定）**: 型番直後に区切り無しで英字が続く語（例:「ADC-V724camera」）は「ADC-V724CAMERA」として一体抽出され、allowlist（型番のみ）と不一致になり取扱外扱いになる（fail-closed 側の偽陽性）。日本語の顧客文で型番に英単語が直結する書き方は実質発生しないため受容する。逆に、末尾サフィックスの大文字を必須とする・境界文字で足切りする等の方式は、顧客が小文字で入力する型番（例:「adc-v521ir」）を検出漏れ（fail-open。取扱外型番が「言及なし」として通過フローに漏れる）にするため不採用とした
- 抽出した型番に **allowlist（取扱 7 型番）外が 1 つでも含まれる**場合、LLM を使わず取扱外定型応答（第 4 節）を返す。evaluate は呼ばない（判定・下書きの LLM コストも発生させない）
- 取扱内の型番のみ、または型番なしの場合は通常フローへ
- 監査: 取扱外応答も case に記録する（既存の case 機構。audit_event_id を発行）

### 3.2 材料選別（決定論）

- 回答下書きへ渡す材料（マニュアル抜粋）を選ぶ段階で、**材料テキスト（title + body_ja + body_en のうち空でないもの全ての連結）に取扱外型番の言及があり、かつ取扱型番の言及が 1 つも無い**材料を除外する（2026-08-14 修正: 従来は body_ja / body_en のどちらか一方だけを検査しており、翻訳が missing/stale で body_ja が空文字の節では body_en が検査漏れになっていた）
- 型番言及の無い汎用材料（Wi-Fi 再接続、映像の一般説明等）は通す（共通内容の活用）
- 除外の結果、材料が 0 件になった場合は特別扱いせず既存の判定に委ねる（カバレッジ不足として聞き返しまたはエスカレーションへ自然に倒れる）
- 除外時は debug ログ（section_key / 検出型番）

### 3.3 聞き返しプロンプトへの注入

- system prompt に取扱一覧（第 2 節の表示文字列）を注入し、制約を追加: 「確認質問・選択肢はこの取扱製品の範囲を前提に組み立てる。取扱外の製品名・製品種別を質問や選択肢に出さない」

### 3.4 回答下書きプロンプトへの注入

- system prompt に取扱一覧を注入し、制約を追加: 「材料に取扱製品以外の製品に関する内容が含まれていても、その部分は使わない。取扱外の製品への言及・比較・案内を書かない。当社の取扱有無など会社としての事実は、この一覧と材料に書かれた範囲でのみ述べる」

### 3.5 応答側ゲート（決定論・最終防衛線）

- `/api/reply` の応答確定点（プレーンテキスト正規化と同じ箇所）で、生成由来の応答文（回答下書き・聞き返し・受け止め文）に 3.1 と同じ抽出を適用し、**allowlist 外の型番言及があればその応答を破棄**して各経路のフォールバック定型文へ倒す。warn ログ（route / 検出型番）
- 定型文・決定的ブロック（受付番号等）は対象外（コード組み立てのため混入しない）

## 4. 取扱外定型応答（3.1 用）

「申し訳ありません。{検出型番} は当社では取り扱いがございません。当社で取り扱っている製品は {取扱一覧} です。その他の Alarm.com 製品につきましては、ご購入元または Alarm.com 社へお問い合わせください。」

- 担当者へのエスカレーションはしない（明確なポリシー回答のため）。この方針を変える場合は本節の差し替えで行う
- 文言はコード組み立て（LLM 不使用）。プレーンテキスト

## 5. 適用範囲

- 3.1（質問側ゲート）・3.5（応答側ゲート）は `/api/reply` 経路のみ。`search_manual` / `get_section` 等の MCP 生 tool の入出力は変更しない
- 3.2（材料選別）は `evaluate()` 内部でカバレッジ判定（`decision::decide()`）より前に適用される共通処理であり、`/api/reply` だけでなく MCP の `evaluate_answerability` tool にも同じ経路で効く。したがって `evaluate_answerability` が返す `decision` と `hits` も、取扱外型番のみを言及する hit の除外を反映した値になる（「MCP tool の入出力は変更しない」という前提は 3.2 には当てはまらない）
- 3.2 の allowlist 取得（`product_allowlist()`）が失敗し、かつキャッシュも無い場合は `evaluate()` 自体がエラーを返す（fail closed）。これは `/api/reply` 限定ではなく `evaluate_answerability` にも及ぶ: 製品マスタが未投入（0 件）の schema では `evaluate` そのものが動作しない（第 2 節の fail-closed 検証を参照）
- 3.3 / 3.4 は生成関数の共通変更であり、MCP 経路の下書きにも同じ前提が効く（CS 担当が検分する下書きにも取扱外断定が混入しないのは望ましい副作用として受容する）
- `/api/reply` の `decide_reply_action` は、今ターンの signal 抽出 LLM 呼び出しが失敗し `ExtractionMode::LexiconFallback` になった場合、`Allowed` / `Escalate` の判定結果によらず常に `EscalationReply` を返す（fail-closed）。抽出 LLM が不調な状況では同一 API 経由の回答下書き LLM も同様に不調である可能性が高く、通常フロー（自動回答・聞き返し）を維持するより安全側へ倒す方が実質的な追加コストなしで成立する。MCP `evaluate_answerability` はこの判定を行わない（`decide_reply_action` 自体が `/api/reply` 専用の関数のため）

## 6. テスト

- 型番抽出: 半角/全角・大文字小文字・ハイフン揺れ / 取扱内のみ / 取扱外含む / 型番なし
- 質問側ゲート: 取扱外 → 定型応答（evaluate 不呼び出し）/ 取扱内・型番なし → 通常フロー
- 二段目のコード判定 veto: `surface` または `matched_model` が取扱内型番（ADC- 接頭辞ありの完全一致・断片のサフィックス一致の両方）を指す foreign 参照 → 通常フロー / `surface` が 64 文字超または制御文字（Cc/Cf/Zl/Zp・ゼロ幅）を含む → 通常フロー
- 材料選別: 取扱外のみ言及 → 除外 / 取扱内言及あり → 通過 / 型番なし → 通過 / 全除外 → 既存判定へ
- プロンプト注入: 一覧文字列と制約文言が clarify / draft の system prompt に含まれる
- 応答側ゲート: 取扱外言及の生成文 → フォールバック / 取扱内のみ → 通過
- マスタ取得: キャッシュ利用 / stale 利用 / 初回失敗 → 503
- 二段目確定時の case demotion: `last_decision` が `out_of_scope_product` へ上書きされる / `last_kr_id` と `last_evidence_keys` と `last_evidence_kind` が空文字になる / `question` など既存属性が保持される / 破棄したターンの signal が `excluded_signals` へ追記され、以降の累積から除外される / 除外済み signal が後続ターンで再観測された場合は `excluded_signals` から取り除かれ通常どおり累積へ反映される（除外は永久ではない）/ 未観測の除外は維持される
- 抽出 LLM 障害時のフェイルクローズ: `ExtractionMode::LexiconFallback` のとき `decide_reply_action` が `Allowed` / `Escalate` いずれの判定でも `EscalationReply` を返す

## 7. スコープ外

- カテゴリ違いの質問（「ドアベルの設定は?」）は 3.1 二段目の LLM 解釈（`foreign` 判定）が担う。誤爆（取扱製品の俗称を foreign と誤判定して誤って断る）の発生率は稼働後の実データで観察し、プロンプトの foreign 判定基準を調整する
- 取扱外時のエスカレーション方針の変更（第 4 節の差し替えで対応可能な形にしておく）
- コーパスの取扱ファミリーへの再スコープ（v2 全件取り込み設計の変更）
- CLAUDE.md の ingest_alarmcom 記述（v1 仕様のまま）の訂正は本件 PR に同梱する
- スコープ除外件数の監査計上（3.1 の取扱外応答件数・3.2 の材料除外件数を運用指標として計上する仕組み）— 現状は warn/debug ログのみで、集計・ダッシュボード化は未実装
