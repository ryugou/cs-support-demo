## 1. 採用する設計

homesec の判断は、CS と同じ水準で行わない。CS は問い合わせ対応であり、誤答が事故になるため厳しく倒す。homesec はアドバイザーであり、同じ厳しさを当てると門前払いと質問攻めになる。

| 判断 | CS の水準 | homesec の水準 |
| --- | --- | --- |
| 範囲外 | 厳しく退場する | **退場は禁止軸だけが決める。** `in_domain` が低いことは退場の理由にしない |
| 材料が無い | 事実を主張しない | 一般論として答える。断定はしないが黙らない |
| 聞き返し | 情報が揃うまで聞く | 最小限にする。聞くより先に答える |
| 身の危険 | mandatory で即エスカレーション | 責任範囲内ならアドバイスしたうえで即エスカレーション。責任範囲外・不明なら安全案内のみで、エスカレーションしない |
| 人へ渡す | 確実に渡すことを最優先する | 会話が進まなくなったら、こちらから提案する |

`in_domain` が低いことは「話題として扱えない」でしかなく、「関わってはいけない」ではない。この 2 つを 1 つの軸で扱うと、天気の質問と犯罪の相談が同じ扱いになる。退場させるのは禁止軸だけとする。

閾値は CS と共用しない。同名の軸であっても homesec 単独で実測し、この文書に記録した値を使う。

## 2. 判断軸

判定材料の抽出は LLM と Jev が担い、閾値比較と分岐の決定は Rust 側が持つ。この不変条件は CS と共通である（正本は `specs/production-cs-mcp.md`）。

| 軸 | 型 | 供給元 | 用途 |
| --- | --- | --- | --- |
| `is_prohibited` | noul | Jev | 排除するか |
| `is_personal_danger` | noul | Jev | 安全案内を出すか |
| `in_domain` | noul | Jev | 関わるか、分からないと言うか |
| `is_time_critical` | noul | Jev | 回答の中身を応急策寄りにするか |
| `is_urtect_support` | noul | Jev | サポート経路へ入れるか |
| `wants_contact` | noul | Jev | 取次経路へ入れるか |
| `in_scope_of_responsibility` | bool | Rust（case 属性） | 身の危険のときにエスカレーションするか |
| `conversation_stalled` | bool | Rust（会話状態） | 取次を提案するか |

`in_scope_of_responsibility` と `conversation_stalled` を Jev で判定しない。前者は発話ではなく契約状態から決まり、後者は会話状態の累積から決まる。

## 3. 閾値と測定根拠

本番と同一の Jev エンドポイント（`https://api.typesafe.ai/v1/systemone`、model `jev-latest`）へ、280 件の日本語発話を投げて測定した（2026-09-25）。

| 軸 | 閾値 | 該当する発話 | 該当しない発話 |
| --- | --- | --- | --- |
| `is_prohibited` | 0.5 | 加害の相談 20 件の平均 0.90 | 被害者からの相談 10 件の最大 0.12 |
| `is_personal_danger` | 0.5 | 危険・痕跡 45 件のうち 43 件が 0.5 以上 | 機器の不具合・一般相談で 0.5 以上は 2 件のみ |
| `in_domain` | 0.35 | 住まい・見守り・一般の住まい話題 115 件のうち 114 件が 0.35 以上 | 無関係 30 件は全件 0.35 未満 |
| `is_time_critical` | 0.7 | 0.80〜0.93 | 0.10〜0.16 |

**Jev の criteria は instructions の言い回しで信号強度が大きく動く。** 同一発話・同一 criteria で、instructions を変えただけで `is_personal_danger` が 0.27 と 0.60 に分かれた。質問定義を変更したときは、この文書の測定値を取り直してから閾値を確定する。

### 3.1 閾値で取りこぼすもの

**`is_prohibited`**: アダルトな内容を持ち込む前置き（「アダルトな内容の相談をしてもいいですか」0.26、「露骨な性的内容の相談をしても大丈夫ですか」0.48）は 0.5 を割る。行為そのものではなく打診であるため。次のターンで本題が来た時点で排除できるため受容する。

**`is_personal_danger`**: 隣室の口論（0.33）と、何が起きたか述べない曖昧な申告（0.47）が 0.5 を割る。前者は日常的に起こり毎回安全案内を出すのは過剰、後者は聞き返して具体化するのが正しい応答であるため、いずれも受容する。

**`in_domain`**: 敷地・駐車場に関する防犯相談が 0.35 を割る（「車上荒らしが増えてると聞いて駐車場の防犯を相談したいです」0.32）。criteria が建物としての住まいを中心に書かれており、敷地・駐車場・共用部が弱い。**明確に範囲内の相談が「分からない」側へ落ちるため、これは受容しない。** Issue #66 の実装前に criteria へ敷地・駐車場・共用部を加えて測り直す。

**`is_time_critical`**: 中間帯が厚い（既に起きた被害 0.67、近隣の治安 0.45）。この軸を応答の分岐に使わず、回答の中身を変える用途に限る。中間帯が通常回答へ落ちても不利益は生じない。

## 4. 決定表

上の行から順に評価し、最初に一致した行を採用する。

| 条件 | 応答 |
| --- | --- |
| `is_prohibited` ≥ 0.5 | 排除する |
| `is_personal_danger` ≥ 0.5 かつ `in_scope_of_responsibility` | 安全案内 + 相談への回答 + 即エスカレーション |
| `is_personal_danger` ≥ 0.5 | 安全案内のみ。エスカレーションしない |
| `is_urtect_support` または `wants_contact` の閾値を上回る（閾値未実測、§6 未決事項） | それぞれの経路へ入る |
| `conversation_stalled` | 取次を提案する |
| `in_domain` ≥ 0.35 | 回答する。`is_time_critical` ≥ 0.7 なら今すぐできる応急策を優先して述べる |
| 上記以外 | 分からないと伝え、一言だけ誘導する。会話は閉じない |

身の危険は `in_domain` を参照しない。住まいの話題でなくても、身の危険があれば安全案内を出す。

答えの強さは `in_domain` ではなく材料の有無で決める。材料があれば出典つきで答え、無ければ一般論に限定する。これは既存の接地 2 層（[`2026-08-17-homesec-advisor-design.md`](2026-08-17-homesec-advisor-design.md) §2.2）のままであり、新しい仕組みを足さない。

`in_domain` に上側の閾値を置かない。この軸は話題の該当性を測るものであり、正確に答えられるかを測るものではない。実測でも、住まいに関する話題は軒並み高く出る（住まい一般 40 件のうち 39 件が 0.8 以上）。ここに「一般論に限定する」という別の意味を乗せると、こちらが正確に答えられない事柄（「町内会の当番は何をすればよいか」0.88）が通常の回答へ回る。

`is_urtect_support` と `wants_contact` の救済が必要な根拠: 機器サポートの相談 10 件のうち 4 件、連絡希望 5 件のうち 4 件が `in_domain` 0.35 未満だった。救済が無いと見積もり依頼に「分かりません」と返す。

責任範囲外の相手を担当へ取り次いではならない。助けが来ると誤解させることになる。

## 5. 顧客へ返す文の規律

この節は homesec と CS の両方に適用する。

```
顧客へ返す文では、こちらの内部の仕組みに言及しない。
材料の有無、判定の仕組み、社内の分類名を書かない。

答えを持っていないときは、その事柄を自社が答えるべきかで書き分ける。
- 自社の製品・料金・契約・サポートのこと
  → 当社で確認すべきことである旨を書く
- 他社のことや世間一般のこと
  → 分からないと書き、公式の案内で確認するよう添える

どちらの場合も「お答えできません」とは書かない。
```

**取次を約束してよいのは、コード側が実際に取次状態へ遷移する経路だけとする。** 応答文を生成するプロンプトは判定が確定した後に組み立てられるため、生成文に「取り次ぎます」「確認して折り返します」と書かせても、`AnswerDecision` / `AdvisorAction` は変わらない。回答経路でこれを書かせると、担当者へ渡す記録も状態遷移も作られないまま顧客へ取次を約束することになる。

したがって、取次・折り返しの約束を含む文言は、エスカレーション経路（CS の `ReplyKind::Escalation`）と取次受付経路（homesec の `LeadSolicit`）のプロンプトにのみ置く。回答経路と聞き返し経路のプロンプトには置かない。

**約束と申し出を区別する。** ここで禁じるのは約束（「取り次ぎます」「折り返します」）であり、申し出（「担当者から詳しくご案内できます」）ではない。申し出は顧客が応じたときに `lead_interest` から時間帯受付へ進み、リード記録まで繋がる実在の経路であるため、回答経路と聞き返し経路のプロンプトに置いてよい（homesec の `LEAD_OFFER_MARKER`）。違いは、顧客の応答を待たずにこちらの行動を確定として伝えているかどうかである。

内部用語を禁止語の列挙で止めない。列挙しなかった語が次に漏れる。内部の仕組みに言及しないこと自体を規則とする。

上の形は homesec の実装(`server/src/advisor/draftgen.rs::build_advisor_system_prompt`)の文言そのものである。**CS での読み替え**(2026-10 是正): CS の実装(`server/src/harness/reply.rs::build_reply_system_prompt`)は、本書と homesec の適用状況が異なる次の 2 点で読み替える。

- CS は取扱製品スコープ(Issue #28 §3.4、取扱外の製品・他社への言及・比較・案内を禁じる)を持つため、2 番目の枝「他社のことや世間一般のこと」は「当社の取扱範囲外のこと(取扱外の製品や他社のこと、世間一般のこと)→ 当社では分からない旨を書く。取扱外の製品や他社についての説明・比較・個別の案内は書かない」と読み替え、公式の案内への誘導は書かせない(§5.1 を CS に適用しないのと同じ理由: CS は他社提案をしない)。
- CS は `DisclosureScope`(`ConfirmingWithTeam` / `NoInternalDetails`)を持つため、1 番目の枝「当社で確認すべきことである旨を書く」について、どこまで書けるかはこの開示範囲の指示を優先する(`NoInternalDetails` では踏み込めない)。homesec にはこの区別が無いため、上の形のまま無条件に適用する。

以上はいずれもコード側の実装済みであり、本節の regression テストは `server/src/harness/reply.rs` の `every_prompt_states_the_internal_information_nondisclosure_rule` と `escalation_prompt_forbids_solutions_and_honors_disclosure_scope` が固定する。

**既知の例外**: `server/src/advisor/canned.rs::OUT_OF_DOMAIN_TEXT`(homesec の `in_domain == false` 定型文)は LLM を経由しない定型文のため、上の規律が届かず「お答えできないんです」という表現をそのまま含む。是正は未了。

### 5.1 他社の扱い（homesec のみ）

CS は他社提案をしないため、この節を CS へ適用しない。

```
他社サービスの扱い:
- 他社の料金、契約条件、キャンペーン、プラン内容、機能の有無は、材料に書かれていても
  書かない。推測で補わない
- 選択肢として他社に触れること自体は差し支えない。ただし触れてよいのは
  「どういう種類のサービスがあるか」までで、その会社の条件には踏み込まない
- 具体的な条件を聞かれたら、各社の公式情報で確認するよう案内して終える
```

**他社の情報を材料として保存しない。** 更新を追わないため、保存した時点で古くなり、嘘の供給源になる。プロンプトに社名・製品名を列挙することも、同じ理由で禁止する。

**この規則は材料ストアの状態に依存しない。** `ingest_homesec` に削除経路が無いため、入力記録から除いた `partner_product` も vegapunk には 12 件残存しており（物理削除は Issue #63）、`CATEGORY_MATERIAL_LIMITS` 経由で毎ターン最大 2 件まで注入されうる。この規則は残存材料の有無にかかわらず他社の条件に触れないため、Issue #63 の完了を待たずに有効である。

## 6. 未決事項

**契約者判定の経路**。`in_scope_of_responsibility` を決める材料が存在しない。LINE から得られるのは userId のみで、契約情報と突合する経路が無い。

決定するまでの扱いは「確認できない場合は責任範囲外」とする。この結果、現時点ではすべての利用者が責任範囲外になり、身の危険を検出しても安全案内のみを返す。

決定者はプロダクト責任者、決定時期は homesec を契約者向けに公開する前。影響範囲は決定表の第 2 行のみで、他の行は契約者判定の有無にかかわらず動作する。

**閾値未実測の軸**。`is_urtect_support` の閾値、`wants_contact` の閾値はいずれも未実測である。この 2 軸は Jev から値を観測しただけで、§4 決定表の分岐に使う閾値をまだ決めていない。

決定するまでの扱いは、決定表（§4）の該当行を本書の実測を経ずに実装へ固定しないこととする。

決定者は実装担当者、決定時期は Issue #66（閾値の実測と Jev へのワイヤリング）の着手前とする。実測後は本書 §3 の表を実測値で更新し、§4 決定表のこの行を確定させる。影響範囲は決定表の第 4 行全体（`is_urtect_support` / `wants_contact` の救済）のみである。

## 7. 実装範囲と現行実装との関係

この文書は判断水準、閾値、決定表、顧客へ返す文の規律の正本である。ただし「正本」は各節で適用状況が異なる。

- **§5(顧客へ返す文の規律)は実装・適用済み**(2026-10)。`server/src/advisor/draftgen.rs::build_advisor_system_prompt`(homesec)と `server/src/harness/reply.rs::build_reply_system_prompt`(CS)の両方のプロンプトへ反映されている。
- **§1〜§4(判断軸・閾値・決定表)は Jev 導入後の目標設計であり、現時点では未実装である。** 実装の段取り、Jev の質問定義ファイル、config への `[jev]` 追加、`TYPESAFE_API_KEY` の `homesec-advisor` への注入は Issue #66 で扱う。

**未実装の間の現行挙動(正本)**: homesec の `in_domain` は、本書 §2 の表が将来像として置く Jev 由来の noul(0〜1) ではなく、`server/src/advisor/understand.rs` の `Understanding::in_domain`(`bool`。LLM Call #1 が直接返す)である。`in_domain == false` は、本書 §1「退場は禁止軸だけが決める」という目標設計とは異なり、現状そのまま `AdvisorAction::OutOfDomain`(`server/src/advisor/decide.rs::decide_in_domain_flow`)へ退場する。移行が完了するまで、この判定フローの正本は `2026-08-17-homesec-advisor-design.md` §4.3 である。

homesec の Jev 質問定義は CS の `server/data/urtect/jev-questions.json` と共用しない。判定基準が異なる。
