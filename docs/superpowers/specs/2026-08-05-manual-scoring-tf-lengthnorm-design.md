# manual 検索スコアの TF / 長さ正規化 / 型番除外

| 項目 | 内容 |
|---|---|
| 目的 | 無関係な記事が正解記事より高スコアになる構造を解消し、判定の再現性を回復する |
| 読者 | `manual::retrieval` を触る実装者と、閾値を調整する運用者 |
| 正本の範囲 | `score_against_corpus` のスコア定義、型番 run の扱い、kill switch、受理条件 |
| 関連文書 | `specs/production-cs-mcp.md`（3 層判定と閾値の正本）、`docs/superpowers/specs/2026-07-22-ingest-alarmcom-design.md`（alarm.com が製品非依存である根拠） |

## 何が壊れているか（実測）

本番で観測した実例。質問「ADC-V724 を使っていますが、パスワードを忘れてしまいました」に対する上位ヒット:

| 順位 | 記事 | score | 関連性 |
|---|---|---|---|
| 1 | アクセス制御ドアコントローラーの固定 IP 設定 | 0.716 | **無関係** |
| 2 | ビデオデバイスの帯域幅要件 | 0.673 | **無関係** |
| 3 | **パスワードの変更またはリセット** | 0.603 | **これが答え** |
| 4 | ログインできない場合 | 0.603 | 関連 |
| 5 | パートナー様向け（`/Partner` ルート＝ハブページ） | 0.603 | **目次的な寄せ集め** |

質問は `['adc', 'v724', '使', 'パスワード', '忘']` の 5 run に分解される。現行スコアは

```
score = Σ_{matched} idf(r) / Σ_{all} idf(r)     （カバレッジ率・bool 一致）
```

### 原因 1: 型番 run が正解記事を構造的に減点する

alarm.com の記事は**設計上あえて製品非依存**（`ingest_alarmcom` は `DESCRIBES` を張らない）。正解記事に `ADC` も `V724` も 1 度も出てこない。この 2 run は**分母に入るが分子には永久に入らない**ため、正解記事はどれだけ完璧に答えていても上限で頭打ちになる。

一方、無関係な記事は型番一覧やスペック表で `ADC-...` を含むため、話題と無関係にマッチする。`v724` は珍しい語で IDF が高く、②は「帯域幅表に V724 と書いてあるだけ」で大きく加点されている。

**型番を書いて質問すると、正解の汎用記事ほど順位が下がる**という逆転が構造的に起きる。型番を入れるのは CS では自然な聞き方なので、実運用で常時踏む。

### 原因 2: TF が無く「主題」と「ついで」が同点になる

`run_matches` は bool を返す。正解記事は `パスワード` を 20 回以上含む（記事の主題）が、①は **1 回**しか含まない —— それも DIP スイッチの初期値説明「ユーザー名: admin **パスワード**: password」である。①の `忘` も「設定を元に戻すことを**忘れ**ないでください」で、質問と全く無関係な文脈。

**両者が同じ 1 点**になる。今回の誤りの大半はここに由来する。

### 原因 3: 長さ正規化が無くハブページが残る

⑤は `/Partner` のルートページで、多数の話題を寄せ集めた長文。話題語を複数回含むので **TF を入れても落ちない**。alarm.com のような KB は構造的にハブページを持つ（`/Partner`、`/Customer`、各カテゴリトップ）ので、これは常在するノイズである。

### 帰結: 判定の非決定性

③④⑤が **0.6028153896331787 で完全に同点**になり、閾値 0.600 の直上に 3 件が並ぶ。わずかな corpus 変動で `escalate`（実測 0.561）と `allowed`（0.603）を跨ぐ。**同じ質問で回答したりしなかったりする**のは、スコアが内容を反映していないことの帰結である。

## 採用する設計

### スコア定義

```
score = Σ_{r ∈ runs} idf(r) × w(r, doc) / Σ_{r ∈ runs} idf(r)

idf(r) = ln(1 + N / (1 + df(r)))                                （現行のまま）

               tf(r, doc) × (k1 + 1)
raw(r, doc) = ────────────────────────────────────────
               tf(r, doc) + k1 × (1 - b + b × len/avg_len)

w(r, doc)   = min(1.0, raw(r, doc))                             （0〜1 に切り詰める）

k1 = 1.2   b = 0.75                                             （BM25 標準値。調整しない）
len        = doc の NFKC 正規化後の文字数
avg_len    = 採点対象コーパスの len 平均
```

**カバレッジ率の枠を維持する**理由は、`best_manual_score` が回答可能性の閾値（low 0.6 / mid 0.8 / high 0.95）と**絶対値で比較される**ため。BM25 のような上限なしのスコアへ全面置換すると、3 閾値すべてを実測で取り直す必要があり、本改修の時点ではその実測ができない（下記「測定できないこと」）。

### 分子の `(k1 + 1)` と min クランプが要点（素朴な `tf/(tf+1)` を採らない理由）

素朴な飽和関数 `tf/(tf+1)` だと、**平均長の記事で 1 回言及**が `0.5` になる。全 run を 1 回ずつ含む的確な記事のスコアが `1.0 → 0.5` に落ち、**閾値 0.6 を割って escalate に倒れる**。「短く簡潔に答えている記事ほど不利」という、直したい歪みと同じ種類の歪みを新たに作ることになる。

BM25 本来の形は分子に `(k1 + 1)` を持つ。`tf = 1` かつ `len = avg_len` のとき

```
raw = 1 × (k1 + 1) / (1 + k1 × 1) = 1.0
```

と**ちょうど 1.0** になる。つまり **`min` クランプ後の値は現行の bool 一致（1.0）と一致する**。

この設計の帰結を正確に述べる:

- **スコアは現行から下がる方向にしか動かない。** 上限は現行と同じ 1.0
- 下がるのは**平均より長い記事で言及回数が少ない run** だけ。これが除きたいノイズそのもの（①②⑤はいずれも長文 × 低 tf）
- **平均長以下の記事は、1 回の言及でも現行どおり満点**を得る。短い記事が不利にならない
- したがって **TF は単独では効かず、長さとの相互作用としてのみ効く**。「TF を入れた」ではなく「長い記事の薄い言及を減点する」が実態である

閾値の意味が保たれる（満点の条件が変わらない）ので、3 閾値の取り直しが不要になる。これが `min` クランプを許容する理由でもある。平均長の記事において `tf = 2` と `tf = 20` は区別されなくなるが、**その区別は本件の誤りの原因ではない**（①の `パスワード` は tf=1 かつ長文）ので、区別を捨てて閾値互換を取る。

### `k1` / `b` は調整しない

BM25 標準の `k1 = 1.2` / `b = 0.75` を使い、**本改修ではチューニングしない**。測定できない状態で独自の値を選ぶのは、根拠のない定数を 2 つ増やすだけで害の方が大きい。実測できるようになってから調整対象にする。

### bigram 救済で一致した漢字 run の tf

`run_matches` は直接一致しない漢字 run を bigram 一致率 50% 以上で救済している（`設定方法` → `設定`/`方法`）。この経路では**出現回数を定義できない**ため、**`tf = 1`（非ゼロ最小）** とする。救済は元々「取りこぼしを防ぐ」ための弱い一致なので、TF でも最弱に置くのが一貫している。

### 型番 run の除外

snapshot の `Product` ノードから `model` + `aliases` を集め、**`content_runs` と同じ関数で分解**して除外集合を作る（`ADC-V724` → `{adc, v724}`）。分解方法を揃えることが要点で、揃えないと除外が効かない。

質問の run からこの集合に含まれるものを落とす。**型番は構造（`DESCRIBES` 辺・`product_key`）で扱い、本文テキストマッチには使わない**という既存の設計意図を、スコアラにも守らせる。

**端境**: 質問が型番だけの場合（例:「ADC-V724」）は run が空になる。既存の「run が取れない質問（全ひらがな等）」と同じ legacy フォールバックへ落とす。

### kill switch

`[harness] manual_scoring_v2_enabled`（既定 **false**）。**TF / 長さ正規化 / 型番除外の 3 つをまとめて**切る。個別フラグにすると組み合わせが 8 通りになり、デモ中の切り分けが実行不能になる。

`config.cloudrun.toml` でのみ true にする。デモで劣化が見えたら 1 行で戻せる。

## 期待される効果（実データでの検算）

型番除外後の run は `{使, パスワード, 忘}`。

| 記事 | `使` | `パスワード` | `忘` | 長さ | 期待 |
|---|---|---|---|---|---|
| ③正解 | 多数 | **20 回以上** | 数回 | 中 | **最上位** |
| ①固定 IP | 多数 | 1 回 | 1 回 | 長 | 下がる |
| ②帯域幅 | 多数 | 1 回 | **0 回** | 長 | さらに下がる |
| ⑤ハブ | 多数 | 数回 | 数回 | **極長** | 長さ正規化で下がる |

③が閾値 0.600 を余裕を持って超え、同点の並びが解消する見込み。**これがテストで固定する対象**である。

## 測定できないこと（明示）

**`verify_alarmcom` による corpus 全体の recall 測定は、本改修の時点で実施できない**（vegapunk 側が別作業中で不介入の指示があるため）。

したがって本改修が保証するのは:

- **実データ 5 記事に対する期待順位**（決定論的な単体テストで固定）
- **スコアが 0〜1 に留まること**（型による保証ではないので、テストで固定）

保証**しない**こと:

- corpus 全体での recall@5 / recall@1 が改善すること
- 既存の閾値（0.6 / 0.8 / 0.95）が改修後も適切であること

**スコアは下がる方向にしか動かない。** 上限は現行と同じ 1.0 で、平均長以下の記事は現行と同値を保つ。下がるのは平均より長い記事だけである。

それでも **escalate 側へ倒れる質問は出る**。alarm.com には長文記事が実在し、そこにしか答えが無い質問では正解記事自身が減点される。**これが本改修の主要リスク**であり、kill switch を置く理由でもある。「長い記事にしか答えが無い」ケースの頻度は corpus 全体を測らないと分からず、それは本改修の時点で測れない。

## 受理条件

1. 実データ 5 記事のテストで、③が最上位かつ①②⑤より明確に高いこと
2. 型番のみの質問が legacy フォールバックへ落ちること
3. kill switch off で従来のスコアと完全に一致すること（回帰が無いことの担保）
4. 既存テストを 1 件も壊さないこと
5. **vegapunk 復旧後**: `verify_alarmcom` で recall を before/after 測定し、閾値の妥当性を再確認する（本改修の完了条件ではなく、後続の必須作業として記録する）

## スコープ外

- ベクトル経路の合成方法（`score = text.max(vector)` の `max` が粗いという課題は別件）
- 閾値そのものの較正
- signal を使ったリランク（型番除外と TF で足りるかを先に見る）
- `verify_alarmcom` の eval 改修

## 制約

- Python / TypeScript を使わない
- スコアは 0〜1 を保つ（閾値の枠組みを壊さない）
- 既存の構成・命名・型に合わせ最小差分
- Conventional Commits。作業ブランチは `feat/customer-reply-draft`
