# 答えられる部分は答え、答えてはいけない部分だけを取り次ぐ

## 1. 原則と採用する設計

原則: **答えられるものは答える。答えてはいけない部分だけを取り次ぐ。** 取り次ぐ項目が含まれているからといって、応答全体を定型の取次文に切り替えない。

実測の例: 「導入にどれくらいの費用がかかるの？」に対し、現行は `initial-cost-quote`（mandatory）にマッチして「初期費用はお客様の状況によって異なりますので、担当者におつなぎします。」+ 受付番号だけを返した。料金ページ（`ingest-urtect-lp`）には月額利用料金（1 台 1,540 円税込/月、2 台 2,640 円、3 台 3,960 円）と「別途設置工事費用がかかります」が投入済みで、月額は答えられた。

採用する設計:

1. **判定（`decide`）は変えない。** 第 1 層・第 2 層のマッチ、エスカレーション事象、受付番号、経路、監査はこれまでどおり。
2. **応答の合成を変える。** 取次（`Escalate`）のとき、材料が質問に十分関連していれば、材料から答えられる部分の下書きを生成し、**下書き + 取次の決定論ブロック（受付番号・対応時間・希望時間帯の聞き取り）** を 1 通にする。下書きには「取り次ぐ項目」を渡し、その項目については内容に踏み込まず担当者がご案内する旨だけを書かせる。
3. **答えられる材料が無いときだけ**、現行どおり定型の受け止め文（`customer_ack`、無ければ LLM 生成の受け止め文、無ければ固定文）+ 決定論ブロックに落ちる。
4. **取次を伴わない回答（`Allowed`）** も同じ下書きプロンプトを使う。取り次ぐ項目が空なので取次文も受付番号も付かない（#73 の「月額いくら」はこちら）。

対象: `/api/reply`（LINE 経由）と MCP `evaluate_answerability`。homesec アドバイザー（`advisor/cs_support.rs` の CS 連携モードを含む）は対象外で、現行の挙動を変えない。

## 2. 用語

- **取り次ぐ項目（handoff items）**: 判定が `Escalate` のとき、マッチした第 1 層ルールの `condition` の signal、または第 2 層の禁止領域の `domain_signals` の signal それぞれの `customer_label`（lexicon の顧客提示用ラベル。例: 「初期費用・設置工事費に関するご質問」）。重複は除く。順序は lexicon の宣言順。内部名（`signal` の識別子、`rule_id`、`route`）は顧客向け文面に出さない（現行の不変条件）。
- **関連十分**: `best_manual_score >= thresholds.low`（`Allowed` の判定に使う下限と同じ値）。取次のときに部分回答を試みる条件として使う。閾値を別に持たない。

## 3. 振る舞い

### 3.1 部分回答の可否（決定論）

取次（`Escalate`）のターンで、次をすべて満たすときだけ部分回答の下書きを生成する。

- 判定が `Escalate` で、`hearing`（聞き返し契約）による `Clarify` ではない。
- 取り次ぐ項目が 1 つ以上ある（第 1 層または第 2 層のマッチによる取次）。第 3 層の取次（根拠不足・確信度不足）は「答えてはいけない部分」ではなく「答える根拠が足りない」なので、部分回答の対象にしない（材料の関連度が下限を超えていても試みない）。
- `best_manual_score` が関連十分である。
- その case が既に取次済みではない（`CaseConvState::is_already_escalated()` が `false`。取次済みなら現行の `build_already_escalated_reply` のまま）。
- 下書き生成が有効（`customer_reply_draft_enabled = true` かつ LLM 有効）。

いずれかを満たさないときは現行どおり（§1 の 3）。

### 3.2 下書きの入力契約

`draft_customer_reply` に次を加える。

- `handoff_items: &[String]`（§2 の customer_label の列。`Allowed` のときは空）。

system prompt（`reply::build_reply_system_prompt`）に次の指示を加える。文言は既存プロンプトの文体に合わせる。

- 材料で答えられることは答える。材料に無いことは答えない（現行どおり）。
- **費用・料金・条件を答えるときは、次を分けて書く**: 材料に金額や値があるもの（そのまま書く）、条件で変わるもの（材料にある範囲で何で変わるかを書く）、材料に値が無く担当者が確認するもの（項目名だけ挙げる）。
- `handoff_items` が空でないとき: その項目については、金額・可否・条件を一切書かず、「〈項目〉は担当者がご案内します」の趣旨だけを書く。各項目を必ず 1 回は挙げる。受付番号や対応時間は書かない（決定論ブロックが付くため）。
- 材料が質問のどの部分にも答えていない場合は、本文を書かず固定トークン `NO_ANSWER` だけを出力する。

user message には現行の材料（上位 3 件・各 2,500 字まで）と質問・履歴に加えて、`handoff_items` を列挙する。

**材料の受け渡し（既存の構造的な遮断の置き換え）**: 現行の `build_reply_brief_with_resolution` は `Escalate` のとき材料（`excerpts`）を常に空にしている（取次応答が受け止め文だけだった時代の「構造的な漏洩防止」）。本書では、§3.1 の部分回答の条件を満たすときに限り、`Escalate` でも `Allowed` と同じ材料（上位 3 件・各 2,500 字まで）を渡す。漏洩防止は、プロンプトの指示（取り次ぐ項目に踏み込まない）、既存の egress gate、§3.5 の決定論の歯止め（ラベル網羅・金額断定の検出・`NO_ANSWER`）の 3 層で代替する。条件を満たさない `Escalate`（関連不十分・取次済み・下書き無効）では下書き自体を生成しないので、材料は従来どおり渡さない。取り次ぐ項目に関する記述を含む材料（例: 料金ページの「別途設置工事費用がかかります」）も除外しない。除外すると「設置工事費は別途かかる」という事実すら言えなくなるためで、金額や条件に踏み込まないことはプロンプトと歯止めで担保する。

### 3.3 応答の合成（`/api/reply`）

`build_escalation_reply_text` を次のように変える。

1. 既に取次済み → 現行どおり。
2. 部分回答の下書きがある（§3.1 を満たし、`NO_ANSWER` ではなく、§3.5 の歯止めを通過） → `assemble_escalation_reply(下書き, 決定論ブロック)`。受け止め文（`customer_ack` / LLM 生成 / 固定文）は使わない。
3. それ以外 → 現行どおり（受け止め文 + 決定論ブロック）。

`ReplyAction::EscalationReply` の種別・エスカレーション事象・`awaiting_time_pref` の遷移は変えない。

### 3.4 MCP `evaluate_answerability`

`Escalate` のときも `customer_reply_draft` に部分回答の下書きを入れる（`Allowed` と同じフィールド）。tool description に「取次判定のときの下書きは、材料で答えられる部分だけを含み、取り次ぐ項目には踏み込まない。受付や取次の案内文は含まない」と明記する。`NO_ANSWER` のときは `null`。

### 3.5 安全側の歯止め（決定論）

下書きを採用する前に次を検査し、1 つでも失敗したら下書きを捨てて §1 の 3 に落ちる（理由を `tracing::warn!` に出す。発話本文は出さない）。

1. 既存の egress gate（NG 辞書）と取扱外型番ゲート（`gate_customer_reply_draft`）を通過する。
2. `handoff_items` の各ラベルが下書きに 1 回以上現れる（取り次ぐ項目を黙って答えていない、または黙って落としていないことの確認）。
3. `handoff_items` のラベルを含む文（「。」区切り）に、金額や数量の断定（数字の直後の `円` / `％` / `%`）が含まれない。
4. 下書きが `NO_ANSWER` でない。

ラベルは lexicon の `customer_label` をそのまま照合する（部分一致・正規化はしない。ラベルの表記揺れは lexicon 側の責務）。

### 3.6 下書きの省略規則の改訂

`2026-10-05-skip-unused-draft-and-ack-log-design.md` §2.2 の「`Escalate` のときは下書きを生成しない」を、「`Escalate` でも §3.1 を満たすときは生成する」に改める。`ReplyDraftPolicy::SkipWhenUnused` に、取次済みかどうか（`already_escalated: bool`）を加える。呼び出し側（`api.rs`）は `CaseConvState` から渡す。`Always`（MCP）は取次済みの概念が無いので §3.1 の第 3 条件を無視する。

## 4. 不変条件

- 判定・経路・エスカレーション事象・監査の内容は本変更で変わらない。
- 取り次ぐ項目について、金額・可否・条件を顧客に提示しない。
- 内部識別子（signal 名、`rule_id`、`route`）を顧客向け文面に出さない。
- 材料に無い金額・条件を書かない（既存の下書きの不変条件）。
- homesec アドバイザーの応答は変わらない。

## 5. 既知の限界

- 取り次ぐ項目に関する断定の検出は、数字 + 単位の形に限る。「無料です」のような単位を伴わない断定は検出しない（egress gate の NG 辞書で補う）。
- 材料の関連度が低い（`best_manual_score < low`）ときは部分回答を試みない。質問の一部だけが材料にある場合でも、検索スコアが低ければ現行の定型文になる。
- 同じ応答で「答えた部分」と「取り次いだ部分」を監査上は区別しない（監査には従来どおり判定と経路が残る）。

## 6. テスト

| 対象 | 固定する内容 |
| --- | --- |
| 取り次ぐ項目の導出（純関数） | 第 1 層ルールの `condition`、第 2 層の `domain_signals` から `customer_label` の列ができる。重複除去。lexicon に無い signal は含めない（warn） |
| 部分回答の可否（純関数） | `Escalate` + 関連十分 + 未取次 + 下書き有効 → 可。`Clarify`、関連不十分、取次済み、下書き無効のそれぞれで不可 |
| プロンプト | system prompt に費用の 3 分類の指示と、取り次ぐ項目に踏み込まない指示が含まれる。user message に `handoff_items` が列挙される。空のときは列挙しない |
| 歯止め（純関数） | ラベル欠落で不採用。ラベルを含む文に `1,540円` があれば不採用。`NO_ANSWER` で不採用。すべて通れば採用 |
| 応答の合成 | 下書きあり: 下書き + 決定論ブロック、受け止め文なし。下書きなし: 現行の受け止め文 + ブロック。取次済み: 現行の `build_already_escalated_reply` |
| `evaluate` | `Escalate` で §3.1 を満たすとき下書き LLM が 1 回呼ばれ、`customer_reply_draft` が入る。満たさないときは呼ばれず `null` |
| 省略規則 | `SkipWhenUnused { already_escalated: true }` では `Escalate` の下書きが生成されない |
| 既存の挙動 | `Allowed` の下書き、`customer_ack` の適用規則（単一マッチ）、エスカレーション事象、homesec の既存テストが通る |

## 8. 対象外

- 判定ロジック（`decide`）の変更、ルールや lexicon の変更。
- 費用項目の名前や金額をコード・設定に持つこと（料金ページの更新に追従させるため、材料からのみ得る）。
- homesec アドバイザーへの適用。
