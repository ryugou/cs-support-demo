## 1. 採用する設計

`/api/reply`（CS の経路）は、顧客の発話に登録名称から 1 文字だけ違う表記（以下、タイポの表記）があれば、回答・聞き返し・取扱外の定型応答の代わりに、その表記と候補を並べた確認を 1 回の返信で返す。
次の発話を確認への返答として LLM で分類し、確定・否定・訂正・見送りはコードが決める。
確定した製品はその案件の製品特定に使い、確定した社名は把握済み事項として相談に添える。確定した名称で、確認の前に受けていた相談を続ける。

- 照合は決定論で行う（§2）。登録名称がそのまま書かれていれば（大小文字・全半角・記号の違いを含む）、LLM の製品参照の結果と抽出モードによらず、その製品を特定済みにする。
- タイポの表記は、LLM の製品参照が `matched` と返しても、確認なしで特定済みにしない（`ambiguous` として扱う）。タイポの表記に当たらない略記・俗称（例: `V724`）の `matched` は従来どおり使う。
- 名称の確認を挟まないターン: 第1層 mandatory または第2層で取次が決まったターン（即時の取次。`EvaluationOutcome.immediate_handoff`）、signal 抽出の LLM が失敗したターン（`LexiconFallback`）、取次済みの案件、LLM 未設定の構成。
- MCP の `evaluate_answerability` と homesec advisor（CS サポートモードを含む）は対象外で、照合も確認も行わない（`ProductNameMatching::LlmReferencesOnly`）。
- 返信APIのリクエスト・レスポンスの項目は変えない。会話ターンの `reply_kind` に `name_confirm` を加え、確認を返したターンの監査イベントの判定を `name_confirmation` とする。管理画面は `name_confirm` を「名称確認」と表示する。

## 2. 照合の規則

名称カタログは、問い合わせ先の schema の Product ノードの `model`・`name`・`aliases`（カンマ区切り）と、`status` が `active` の Company ノードの `name`・`aliases`（§6）だけから作る。
候補として示す表記は、型番なら型番、製品名と製品の別名なら製品名（`name`）、社名と社名の別名なら正式な社名とする。

- 比較は、文字のまとまり（基底文字と後続の結合文字）ごとに `resolve::normalize_key`（NFKC・小文字化・英数字と文字以外の除去）を適用した列で行う。除去された記号・空白は語の区切りとして扱う。
- 一致: 正規化した列に登録名称（2 文字以上）がそのまま現れる。区切りのない ASCII 英数字どうしの間で切れる範囲は一致としない（`ADC-V7245` は `ADC-V724` に一致しない）。重なる一致は長い方を採る。
  1 つの表記が複数の登録名称に一致した場合は、どれか 1 つに決めず確認する。
- タイポの表記: 一致と重ならない範囲で、登録名称（5 文字以上）から 1 文字の置換・挿入・削除、または隣り合う 2 文字の入れ替えだけ違う表記。語の途中で切れる範囲の規則は一致と同じ。
  重なり合うタイポの表記は 1 つにまとめ、すべての候補を並べる（`ADC-VC728P` → `ADC-VC729P`、`ADC-VC727P`）。
- 顧客の表記の範囲: 誤った文字（置換・挿入した文字）が名称の文字と同じ文字種（ASCII 英数字・ひらがな・カタカナ・漢字・その他）である読み方のうち最も長い範囲とし、そのような読み方がなければ最も短い範囲とする。
  `株式会杜` は `杜` を含めて示し、`ADC-VC729の` の `の` は名称の外の語とみなして含めない。
- 1 文字より多く違う表記、短い部分一致（2 文字未満の一致、5 文字未満の名称のタイポ）、意味が近いだけの表記は候補にしない。距離の値や `fuzzy_score` で候補を決めない。
- 照合の根拠は名称カタログだけで、特定の文字列・接頭辞に依存する分岐を持たない。取扱外ゲートの型番検出式（`model_token_regex`）は変えない。

## 3. `/api/reply` の処理順

`reply_handler` の既存の処理順に次を組み込む。番号は実行順。

1. 取扱一覧を取得した直後に、`case_id` の案件から確認状態（§4）を読む。LLM が設定されていれば、問い合わせ先の社名（§6）も読む。
2. 確認待ちの表記があれば、発話を確認への返答として分類し（§5.2）、確認状態をメモリ上で更新する（まだ保存しない）。
3. 質問側ゲート一段目（product-scope §3.1）: 発話の一覧外の型番のうち、§5.1 の「候補を示せる表記」に当たらない最初の型番で、取扱外の定型応答を返す。
   2 で返答を解釈したのに確定した名称も確認待ちも残らず、否定された表記が一覧外の型番であるときも、その型番で取扱外の定型応答を返す。
   定型応答を返す前に 2 の結果を保存する（この経路は製品の切り替えを検知しないため、同じ案件に保存する）。
4. 製品の切り替え（#61）を検知したターンは、2 の結果を捨て、新しい案件として確認状態を空にし、名称の確認を有効に戻す（旧案件が取次済みでも有効にする）。旧案件の確認状態は変えない。切り替えでなければ 2 の結果を保存し、製品を確定したら案件の `product_models` にも加える。
5. 希望時間帯の受付（会話フロー §5）は従来どおり行う。取次済みの案件では名称の確認を行わないため、確認待ちが残っていても割り込まない。
6. `evaluate()` を呼ぶ。製品参照は §1 のとおり登録名称の照合で絞り、直近の顧客発話の窓の製品参照にも同じ照合を適用する。最新の確定した製品を、呼び出し元が明示した製品（`product_key`）として渡す。
   製品を確定したターンは、窓のうち確定した表記を含む顧客発話（表記を候補の表記に置き換えたもの）と今回の発話を改行で連ねた文で、マニュアルを検索する。
7. 質問側ゲート二段目: `foreign` と確定した製品参照の表層が §5.1 の「候補を示せる表記」に当たるときは、取扱外の定型応答を返さない。
8. 確認の要否を決め（§5.1）、必要なら確認文を返す。`evaluate()` が案件へ書いた判定・signal の累積・監査は残し、下書きは応答に使わない。
9. 確認しない場合は従来どおり応答を決める。聞き返しの把握済み事項に、確定した名称（「確認済みの製品」「確認済みの社名」。製品名で確定した製品は型番も添える）、案件の `product_models` のうち型番と異なる製品名を持つ製品（「特定済みの製品: {製品名}（型番 {型番}）」）、顧客が違うと答えた候補（返信に書かない旨を添える）を加え、聞き返しに渡す取扱製品カタログから否定された製品を除く。
   否定で候補が残らなかったターンは、登録名称と一致しなかった顧客の表記も把握済み事項に加え、その表記を含む直前の顧客発話と今回の発話を連ねた文を聞き返しの問い合わせとして渡す。顧客が書いた表記を受け止めたうえで、候補を絞る情報を尋ねるため。
   聞き返しの文面が否定された候補をそのまま書いた場合は `FALLBACK_CLARIFY_TEXT` に倒し、`request_id`・`case_id` を付けて warn を出す。

## 4. 確認状態

保存先は `support_case` の属性 `name_confirmation`（JSON 文字列）で、`/api/reply` だけが read-merge-write で書く。属性は 3 つの schema ファイルに宣言する（homesec では書き込まれない）。属性のない案件は空の状態として扱う。

| フィールド | 内容 |
| --- | --- |
| `pending` | 確認待ちの表記（最大 3 件）。`surface` は顧客の表記（発話の元の文字列）、`surface_key` は正規化した表記、`suggestions` は候補（1〜5 件）、`asks` は提示した回数（0〜2）、`reason` は次に確認するときの聞き方（`first`・`choose`・`already_told`） |
| `confirmed` | 確定した名称（最新 16 件）。`surface_key` と `target`。`target` は `kind`（`product` か `company`）、`id`（製品は型番、社名は正式な社名）、`display`（示す表記） |
| `denied` | 顧客が否定した候補の `kind` と `id`（最新 16 件） |
| `dismissed` | 確認を見送った表記の `surface_key`（最新 16 件） |

不変条件:

- 4 つのフィールドはすべて必須。未知のフィールド・未知の `kind`・`reason`、空の文字列、件数や `asks` の上限超過、そのまま返すと安全でない `pending.surface` を含む状態は、読み出しで拒否する（§7）。
- 確定・見送りした表記（`surface_key`）は、同じ案件で再び確認しない。否定された候補は、同じ案件で再び候補にしない。
- 最新の確定した製品を、その案件の製品として判定に使う。社名の確定は製品の特定に使わない。

## 5. 確認の提示と返答の解釈

### 5.1 提示

確認の対象は、確認待ちの表記、今回の発話のタイポの表記、直近の顧客発話の窓（最大 6 件・合計 2,000 字。`reply::customer_history_window`）のタイポの表記の順に、最大 3 件とする。複数あれば 1 回の確認にまとめる。
候補からは、否定された候補と、今回の発話に登録名称がそのまま書かれた候補を除く。
次の表記は対象から除く: 確定・見送り済みの表記、候補が残らない表記、そのまま返すと安全でない表記（64 文字超、または制御文字・ゼロ幅文字を含む。product-scope §3.1 (c) と同じ検査）。
安全でない表記の除外は、否定の返答から拾って確認待ちにする表記（§5.2）にも同じく適用し、読み出した確認状態の検証（§4）でも拒否する。
窓から拾った表記には、以前のメッセージの表記であることを確認文の材料に添える。提示のたびに `asks` を 1 増やす。

「候補を示せる表記」は、このターンの確認の対象（上の規則で選んだ最大 3 件）に入る表記か、顧客が確定済みの表記（`confirmed`）とする。取扱外ゲートの一段目・二段目（§3 の 3・7）と確認の提示（§3 の 8）は、この同じ判定を使う。
同じ発話に登録名称がそのまま書かれた候補しか持たない一覧外の型番（`ADC-VC729PとADC-VC729の違い` の `ADC-VC729`）は、対象にならないため取扱外の定型応答になる。4 件目以降のタイポの表記も同じく対象外である。名称の確認が無効の構成・案件（§1）では、どの表記も候補を示せない。

### 5.2 返答の分類と遷移

分類の LLM には、確認待ちの表記と候補、顧客が直前に受け取った確認文（履歴の最後の assistant 発話。あれば）、今回の発話を、それぞれ区切りタグを無害化したデータブロックで渡す。
肯定で始まる返答は、症状の説明が続いても名称の確認への肯定として分類させる。
分類の LLM の出力は `{"reply_type": "answer" | "already_told" | "unrelated", "answers": [{"no": 番号, "verdict": "yes" | "no" | "choose" | "unknown", "chosen": 表記または null}]}` だけを受け付ける。
未知の値、範囲外や重複の番号、`choose` で `chosen` が空の出力は、分類の失敗として扱う（§7）。

| 返答 | 遷移 |
| --- | --- |
| `unrelated`（確認に答えず別の相談を始めた） | 確認待ちをすべて見送り、今回の発話を新しい相談として通常どおり扱う。案件は変えない（#61 の切り替えを検知したターンを除く） |
| `already_told`（名称は最初に伝えたと指摘しただけ） | 同意とはみなさず、同じ候補をもう一度確認する。確認文では最初に受けた表記であることを受け止める |
| `yes`（候補が 1 件） | その候補を確定する |
| `yes`（候補が複数） | 確定せず、候補から選んでもらう確認をもう一度返す |
| `choose` | 選んだ候補（正規化して候補の表記と一致するもの）を確定する。候補にない名称を選んだ場合は `no` と同じ |
| `no`（否定・言い直し） | 提示した候補をすべて否定済みにする。返答に同じ種類（製品か社名）の否定されていない登録名称がそのまま書かれていればそれを確定し、なければ返答のタイポの表記を新しい確認待ちにして同じターンで確認する。どちらもなければ確認待ちを残さない |
| `unknown` | もう一度確認する |

もう一度確認するのは `asks` が 2 未満の表記だけで、2 回提示した表記は見送る。確認のループはこれで 2 回までに止まる。

### 5.3 確認文

確認文は LLM が生成する。渡すのは、確認する表記ごとの顧客の表記と候補（データブロック `<確認する名称>`）と今回の発話（`<顧客からの問い合わせ>`）で、区切りタグは無害化する。
制約は、顧客の表記と候補を一字一句変えずに並べること、候補が 1 件ならはい・いいえで答えられる聞き方、複数なら選んでもらう聞き方にすること、名称以外を尋ねないこと、回答・原因・手順を書かないこと、`<確認する名称>` にない名称を書かないこと。
冒頭の受け止めは一言までとし、症状や状況を「〜とのことですね」と確かめる文を書かない（顧客の「はい」が名称の確認への返事として読めるようにする）。

出力は既存の出口ゲート（`egress_gate`）を通し、さらに次のすべてを満たすことを検査する。

- すべての顧客の表記と候補の表記を含む。
- 登録名称がそのまま書かれている場合、それは提示した候補だけである。
- 取扱一覧外の型番は、確認する顧客の表記だけである（顧客の表記が一覧外の型番でも却下しない）。

LLM の失敗・下書きの打ち切り・ゲートや検査での却下のときは、データから組み立てる次の固定の文型に倒す。

- 表記が 1 件: 「{顧客の表記} とお知らせいただきましたが、{候補} のことでしょうか？」。候補が 2 件なら「{候補1}、{候補2} のどちらのことでしょうか？」、3 件以上なら「…のどれのことでしょうか？」とする。
- 表記が複数: 「お知らせいただいた名称を確認させてください。」の後に、表記ごとに「・{顧客の表記} は {候補} のことでしょうか？」を並べる。

この固定の文型は、会話フロー §10.3 の「顧客向け返信に固定テンプレートを使わない」方針（2026-11-02）の例外として、2026-11-23 にユーザーが採用した。`FALLBACK_CLARIFY_TEXT` に倒すと型番を最初から尋ね直し、失敗時に確認のループが再発するため (Issue #153)。

## 6. 社名の正本と登録手順

社名の正本は、問い合わせ先の schema の `Company` ノード（`schema/cs-support.yml`）とする。

| 属性 | 内容 |
| --- | --- |
| `company_key` | 安定した upsert キー（英小文字・数字・内側のハイフン、1〜64 文字）。ノード ID は `{schema}:gen1:Company:{company_key}` |
| `name` | 正式な社名（100 文字以下、制御文字なし） |
| `aliases` | 別名（カンマ区切り） |
| `status` | `active`（照合に使う）か `retired`（登録から外した。照合に使わない） |

登録の入力は `server/data/urtect/companies.json`（JSON 配列 `[{"key": ..., "name": ..., "aliases": [...]}]`。3 つのフィールドはすべて必須）とする。載せるのは公開されている一般的な名称だけで、顧客の非公開の名称は扱わない。
同梱の `companies.json` は空の配列 `[]` で、社名を 1 件も登録しない。空の配列を投入すると、登録済みの `active` の社名はすべて `retired` になる（社名の確認を止める操作になる）。

登録・更新は `ingest_companies`（`server/src/bin/ingest_companies.rs`）で行う。

1. ファイルを検証する。次のどれかがあれば、vegapunk へ接続する前に失敗する: 999 件を超える社名、未知のフィールド、形式に合わないキー、キーの重複、空・制御文字を含む・長すぎる名称や別名、カンマを含む別名、英数字も文字も含まない表記、正規化すると他の社名や別名と同じになる表記。
2. `schema/cs-support.yml` を schema 名を差し替えて登録・更新する（`ingest_products` と同じ）。
3. `active` の Company ノードを読み、ファイルの社名を `active` で書き、ファイルから外れた社名を既存の属性を保ったまま `retired` で書く。`retired` のノードは書き直さない。社名の変更は、キーを保ったまま `name` を書き換える。書いた件数（`active`・新しく `retired` にした件数）を JSON で出力する。

本番への投入は人が行う。`ingest_companies` はコンテナイメージ（`Dockerfile`）に含めておらず、Cloud Run job も CI の `auto-ingest` の対象もない。
実行するには、本番 vegapunk へ接続できる環境から `--endpoint`・`--token-file`（または `--token-env`）を指定するか、イメージへの追加と job の作成（デプロイ構成の変更）を別に行う。

読み出しは `ProductGate` が取扱製品一覧とは別に、schema 単位に TTL 10 分でキャッシュして行い、`status` が `active` のノードだけを読む。登録から最大 10 分で照合に反映される。
形式に合わないノードは warn を出して除く。Company ノード型を登録していない schema では 0 件になる（vegapunk の `QueryNodes` はノード型を schema と照合しない）。
1 回で読み切れない件数（`active` が 1,000 件以上）は社名の取得の失敗とする。登録手順が 999 件までに限るのはこのため。
社名の取得は取扱製品一覧の取得と分けており、失敗しても取扱製品一覧と返信は失敗させない（§7）。社名を問い合わせるのは、LLM が設定された構成の `/api/reply` の名称確認だけで、取扱製品一覧（MCP・homesec も使う）は社名を問い合わせない。

Punk Records の既存の名称は取得元に含めない。テンプレート（`punkrecord`・`discussion`・`review`）の `Person`・`Channel`・`Topic` などの `name` は会話やレビューから抽出した名称で、社名の正式表記の一覧ではない。schema をまたぐ検索は未実装で、問い合わせ先ごとに 1 つの schema を使うため。

## 7. 失敗・中断時の挙動

| 事象 | 挙動 |
| --- | --- |
| 確認状態が §4 の形式に合わない | 500（`internal`）を返す。状態を推測で補わない |
| 確認状態・案件の読み書きが vegapunk の障害で失敗 | 503（`upstream_unavailable`） |
| Company ノードの取得の失敗（vegapunk の障害、`active` が 1,000 件以上） | warn を出し、期限切れのキャッシュがあればそれを、なければ社名なしで名称の確認を続ける。取扱製品一覧と返信は失敗させない |
| 返答の分類が失敗（LLM の失敗・形式違反） | warn を出し、確認待ちをすべて見送って、今回の発話を通常どおり扱う |
| 確認文の生成が失敗・却下 | §5.3 の固定の文型を返す |
| 確認の監査イベントの記録が失敗 | warn を出し、空の `audit_event_id` で応答する |
| 返答を保存した後に `evaluate()` が失敗 | 保存した確定・否定・見送りは戻さない（ロールフォワード）。同じ返答が再送されたら確認待ちのない通常の発話として扱い、確定した製品で判定する |
| LLM 未設定 | 名称の確認を行わない。登録名称がそのまま書かれた製品の特定は行う |

## 8. 既知の制約

- 確認で確定した製品は、#61 の製品切り替えの検知の対象にしない。確定した製品が案件の既存の製品と違っても案件を切り替えず、`product_models` に加える。切り替えの検知は、従来どおり今ターンの LLM の製品参照だけを見る。
- 社名だけがタイポで製品が特定済みのターンは、`evaluate()` が回答の下書きを作ってから確認を返すことがある。その下書きは使わずに捨てる（LLM のコストとして受容する）。
- LLM 呼び出しは、確認を返すターンに確認文の生成 1 回、確認待ちがあるターンに返答の分類 1 回が加わる。

## 9. #138 との対応

#138（製品名での製品特定）の受入条件と、本件で満たしたこと・満たしていないことを示す。#138 の残りは #138 で扱う。

| #138 の受入条件 | 本件で満たしたこと | 満たしていないこと |
| --- | --- | --- |
| 製品名だけを答えた次ターンで製品が特定済みになり、聞き返しが止まる（テスト） | `/api/reply` は、登録名称（製品名・別名）がそのまま書かれた発話を、製品参照の抽出結果によらず特定済みにする（§1・§2）。製品未特定の聞き返しの次のターンに製品名だけを答える会話で、製品が特定され聞き返しが止まることを、抽出 LLM の結果を空に固定した L2 と、実 LLM の L3 で確認する | MCP の `evaluate_answerability` は照合を行わないため、製品名だけでは特定しない。#138 の「抽出器の入力カタログに製品名を含める」（LLM 側の変更）は行っていない |
| 名前と型番が同じ製品の挙動に変化がない | `name = model` の製品（F-P7）での既存テストと、既存挙動の対照（正式一致・候補のない取扱外・製品切替・時間帯受付・安全エスカレーション）が変わらないことを確認する | なし |
| `cargo fmt --check` / `cargo clippy` / `cargo test` が通り、レビューゲートを通る | 本件の検査で実行する | レビューゲートは本件の独立検査で判定する |

## 10. テスト

- L1（`server/src/harness/name_confirmation/` の各 `tests.rs`）: 照合（一致・4 種の誤り・拮抗・短い部分一致・意味の近さ・語の途中・文字種・カタログだけへの依存）、確認状態の検証と往復、返答の分類の解析と遷移、確認文の検査と固定の文型、社名ファイルの検証と登録手順。
- L2（`server/src/reply_test_harness/name_confirmation/`）: `POST /urtect/api/reply` を、スタブ LLM と vegapunk の代替で複数ターン駆動する。報告された会話、聞き直し済みの会話、製品名・社名、誤提案と確認のループの防止、取扱外・製品未特定・即時の取次の経路、既存挙動の対照、登録手順で投入した社名での確認、§7 の失敗時の挙動（分類・監査の失敗、500・503、社名の取得の失敗）、#138 の会話を確認する。
