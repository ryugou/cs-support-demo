# 会話フロー v1.1: ヒアリングループとエスカレーション応答の文脈化

| 項目 | 内容 |
| --- | --- |
| 目的 | `/api/reply` 経路の会話フローを定める: 聞き返しによる情報収集、文脈化されたエスカレーション応答、希望時間帯の受付 |
| 読者 | 実装エージェント、レビュー担当 |
| 正本の範囲 | ヒアリングループの条件と上限、エスカレーション応答の構成、営業時間の判定、希望時間帯の抽出・検証、case への状態追加 |
| 関連文書 | `docs/superpowers/specs/2026-08-11-answer-api-line-adapter-design.md`（`/api/reply` 契約の正本。本書はその応答決定 §4 を置き換える）、GitHub Issue #17 |

## 1. 採用する設計

`/api/reply` の応答決定を「即答 / 即エスカレーション」の 2 値から、「即答 / **聞き返し（最大 3 ターン）** / 文脈化エスカレーション」の 3 値に拡張する。聞き返しで集まった発話は既存の case 機構（signal 累積 → 毎ターン再判定）に乗るため、判定の仕組み自体は変更しない。エスカレーション応答は「受け止め文（生成）+ 決定的ブロック（受付番号・希望時間帯の伺い・営業時間案内）」の合成とし、期限の断定はしない。

適用は `/api/reply` 経路のみ。MCP tool（`evaluate_answerability`）の入出力・挙動は変更しない。

## 2. 応答の決定（v1 design doc §4 の置き換え）

| evaluate の結果 | 応答 |
| --- | --- |
| allowed かつ下書きあり（truncated でない） | `customer_reply_draft` |
| escalate かつ `clarification_allowed = true` かつ case の `clarify_turns < 3` | **聞き返し**（第 3 節） |
| escalate（上記以外）/ rule_match / allowed で下書き null か truncated | **エスカレーション応答**（第 4 節） |

- `clarify_turns` の上限は config `[api] clarify_max_turns`（既定 `3`）
- フォールバック規則（生成失敗・生成上限による途中切断・egress 却下時に定型文へ落とす）は v1 と同じ思想で、聞き返し・エスカレーションそれぞれに定型文を持つ（第 3・4 節）

**`clarification_allowed` の定義（正本は実装: `server/src/harness/mod.rs` の設定条件）**: 第三層の Escalate かつ reason が `InsufficientDirectness` または `UnknownAddedSignal` のときのみ `true`。第一層（明示エスカレーションルール）・第二層（禁止ドメイン）起因の escalate は決定論で `false`（禁止ドメインの質問に確認質問を返すこと自体が「答えられる可能性」を示唆する漏洩経路になるため、聞き返しは第三層のグレーゾーンに限る）。本書はこの条件を契約として固定し、**第 1・2 層で false になることの退行防止テストを置く**（第 8 節）。

## 3. 聞き返し（ヒアリングループ）

- 生成: LLM に「質問の受け止め + 情報を集めるための確認質問 1〜2 個」だけを書かせる。入力は**顧客質問と判定の不足情報（不足カバレッジ等）と会話段階フラグ（下記）のみ**とし、検索ヒットの title・本文は入力に含めない（title に解決策が書かれた FAQ からの断片漏洩を egress gate だけに頼らないため）。**回答・手順・仕様の内容に加え、対処の示唆・一般的アドバイス（「リセットで改善する場合があります」等、モデルの事前知識由来の助言）を含めることを禁止**するプロンプト制約を置き、egress gate を通す
- **会話段階による出し分け**: 「初回か継続か」はサーバがコードで判定する（リクエストの `history` が非空、または呼び出し元から `case_id` が渡された場合は継続）。継続のとき、聞き返し・受け止め文のプロンプトに「挨拶・感謝・謝罪の定型オープナー（「いつもご利用いただき〜」「ご不便をおかけして〜」等）を書かず、直前のやり取りを受けて本題から始める」制約を加える。初回は現状どおり。判定は決定論（コード）、文面だけ LLM
- 生成失敗・生成上限による途中切断・gate 却下時の定型文: 「状況を詳しく教えていただけますか。製品名、いつから発生しているか、画面にエラー表示があるか、が分かると調査が早くなります。」
- 聞き返しを送信するたび、case 属性 `clarify_turns` を +1 して永続化する（第 6 節）
- 次ターンの顧客発話は通常どおり evaluate に入る。signal 累積により allowed へ変われば即答、変わらなければ本節の条件を再評価する
- 3 ターン消費後も escalate のままなら第 4 節へ。それまでに集まった発話・signal は case 経由で担当者に渡る（既存機構のまま）
- 聞き返し中に顧客が「担当者につないでほしい」等の明示依頼をした場合の脱出は**第一層に委ねる**: 取次依頼の signal（signal 語彙へ追加）を条件とする escalation_rule を 1 件投入する（データ変更、本ユニットに含む）。第一層マッチにより `clarification_allowed = false` となり、ターン残数に関係なく第 4 節へ落ちる
- `clarify_turns` は**エスカレーション応答（第 4 節）の送信時に 0 へリセット**する。同一 case で後日別の話題が来た場合に聞き返しの予算が回復するため。case には明示的なクローズが無く、アダプタのセッション TTL（60 分）が実質の会話境界である点は v1 design doc §6 のとおり

## 4. エスカレーション応答

応答文 = 受け止め文 + 決定的ブロックの連結。

**受け止め文（LLM 生成、egress gate 経由）**: 「ご質問いただいている○○の件、担当者が確認のうえご連絡いたします」に相当する 1〜2 文。○○は顧客質問からの主題の言い換え。回答内容・期限の約束を含めることを禁止する。生成失敗・生成上限による途中切断・gate 却下時の定型文は会話段階で出し分ける（選択はコード。第 3 節の `is_continuation` と同じ判定を使う）:
- 初回: 「お問い合わせありがとうございます。担当者が確認のうえ、あらためてご連絡いたします。」
- 継続: 「担当者が確認のうえ、あらためてご連絡いたします。」（感謝オープナーを含めない）

**決定的ブロック（コードで組み立て、LLM を通さない）**:

1. 受付番号: 「受付番号: {case_ref}」。`case_ref` は `case_id` の UUID 部分の先頭 8 文字。一意ではなく衝突しうる（数万件規模で約 1%）。顧客向け表示専用とし、担当者が受付番号で検索する場合は複数ヒットしうる前提で扱う
2. 希望時間帯の伺い: 「ご連絡のご希望時間帯があればお知らせください（対応時間: {営業時間の表記}）。可能な限り合わせます。」送信時に case 属性 `awaiting_time_pref = true` を立てる
3. 営業時間外の受付案内（受付時刻が営業時間外のときのみ）: 「現在は対応時間外のため、担当者からのご連絡は翌営業時間（{営業時間の表記}）以降となります。」

期限の断定（「1 営業日以内」等の固定 SLA 文言）は置かない。

## 5. 希望時間帯の受付

case の `awaiting_time_pref = true` のとき、次の顧客発話を最初に時間帯返信かどうか分類する。

- 分類と抽出: LLM で `{ is_time_preference: bool, windows: [{ days: "weekday" | "weekend" | "any", start: "HH:MM" | null, end: "HH:MM" | null }], raw: string }` を構造化抽出する。「午後」「夕方以降」等の曖昧表現は windows の start/end を常識的な時刻に正規化させる（例: 午後 = 12:00–18:00）
- `is_time_preference = false` の場合: case 属性 `time_pref_false_count` を +1 し、その発話を通常の evaluate フロー（第 2 節）に流す。**false 分類が 2 回連続したら `awaiting_time_pref = false` に自動解除する**（時間帯に言及しない顧客の全発話へ分類 LLM が挟まり続けることを防ぐ）。true 分類が来たら 0 に戻す
- **抽出インフラの失敗（LLM 呼び出しエラー・応答 parse 失敗）は `is_time_preference = false`（真の分類結果）と区別し、`time_pref_false_count` を増やさない。** 混同すると、一時的な LLM 障害が 2 ターン続くだけで顧客が実際に答えた希望時間帯が恒久的に取りこぼされる（`awaiting_time_pref` が誤って自動解除される）。この場合は `time_pref_false_count` / `awaiting_time_pref` を変更せず、その発話をそのまま通常の evaluate フロー（第 2 節）に流す。**抽出インフラ失敗が連続する場合の解除は case 属性 `time_pref_extraction_error_count`（int、既定 0）で行う**: 失敗のたび +1 し、**3 回**に達したら `awaiting_time_pref = false` かつ `time_pref_false_count = 0` へ自動解除し、自身も 0 へリセットする（`time_pref_false_count` の 2 回連続解除と同じ「解除と同時にカウンタをリセットする」規律）。分類が成功した場合（true/false どちらでも）は 0 に戻す。この判定・保存は Task 6（オーケストレーション層、`/api/reply` ハンドラ）の責務とする（`time_pref.rs` は `Result` を返すだけで、このカウンタ自体は関知しない）
- `is_time_preference = true` の場合、**営業時間との重なり判定はコードで行い、いずれの場合も 1 回で受け付ける（訂正の往復はしない）**:
  - 営業時間と重なる希望: 「承りました。{raw} の時間帯でご連絡できるよう担当者に申し伝えます。」
  - 重ならない希望: 「{raw} で承りました。なお、担当者からのご連絡は対応時間（{営業時間の表記}）の中となるため、ご希望に添えない場合があります。」（曖昧表現の正規化揺れで機械的に突き返さない。最終判断は担当者に委ねる）
  - どちらも `preferred_contact_time = raw`（時間外の場合は「（対応時間外の希望）」を付記）を保存し、`awaiting_time_pref = false`
- 新しいエスカレーション応答（第 4 節）を送るときは `awaiting_time_pref = true` を上書きセットし、`time_pref_false_count` を 0 に戻す
- **解除とエスカレーション再送が同一ターンに重なる場合、再送側が勝つ（意図した挙動）**: false 分類や抽出障害で解除に達しても、その発話の evaluate が新しいエスカレーション応答を送るなら、時間帯を改めて伺うため再武装される。したがって「2 回連続 / 3 回で解除」が効くのは、間に聞き返し・即答が挟まるケースである。LLM 障害が続く間は毎ターン分類 1 回が空振りするが、応答自体はテンプレートで継続するため許容する
- 時間帯受付の応答はすべて定型文組み立て（LLM 生成なし）。抽出だけが LLM で、判定・応答はコード

## 6. 営業時間と case 属性

営業時間は config `[api].business_hours`:

| キー | 既定 |
| --- | --- |
| `days` | `"mon-fri"`（`mon-fri` / `everyday` の 2 値） |
| `start` | `"10:00"` |
| `end` | `"18:00"` |
| `tz` | `"Asia/Tokyo"` |

表記文字列は days/start/end から組み立てる（`mon-fri` → 「平日 10:00〜18:00」）。「営業時間内か」の判定は現在時刻（tz 変換後）と start/end の比較のみ。祝日は考慮しない（v1.1 のスコープ外、担当者側の運用で吸収）。

case ノードへ追加する属性（すべて加算のみ・後方互換）:

| 属性 | 型 | 用途 |
| --- | --- | --- |
| `clarify_turns` | int（既定 0） | 聞き返し回数の上限判定。エスカレーション応答送信時に 0 へリセット |
| `awaiting_time_pref` | bool（既定 false） | 次発話を時間帯返信として解釈するか。false 分類 2 連続で自動解除、新エスカレーションで再セット |
| `time_pref_false_count` | int（既定 0） | 自動解除用の連続 false カウント |
| `preferred_contact_time` | string（任意） | 担当者への申し送り（時間外希望はその旨を付記） |
| `time_pref_extraction_error_count` | int（既定 0） | 抽出インフラ失敗（`time_pref_false_count` とは別枠）の連続回数。3 回で自動解除 |

起動時検証: `[api] enabled = true` のとき、`business_hours.tz` / `start` / `end` / `days`（`"mon-fri"` または `"everyday"` のいずれかであること）はサーバ起動時に検証し、失敗したら `anyhow::bail!` で起動を止める（fail closed）。実行時に `hours.rs` が同じ値を fail-closed で「営業時間外」に倒す経路はあるが、設定ミスに気づかないまま「常に営業時間外」の案内が出続ける事故を起動時点で防ぐ。`days` を検証対象から外すと、`business_hours_label` が未知値を黙って「平日」表示に倒すため、「常に対応時間外」の案内がもっともらしいラベル付きで出続ける同種の事故が別経路から起きる。

**並行更新の制約（Accepted Risk）**: case 属性の保存は read-merge-write（全属性再送）であり、同一 case への並行リクエストを直列化する仕組みをサーバ側には置かない。`/api/reply` の唯一の呼び出し元である LINE アダプタがユーザー単位に処理を直列化している（v1 design doc §6）ため、同一 case の並行書き込みは実運用で発生しない。API を直接呼ぶ別クライアントを追加する場合は、呼び出し側での直列化を契約とする。

## 7. LLM 呼び出しの増分（運用注意）

- 聞き返し生成: escalate かつ clarify 条件成立時に 1 回
- 時間帯抽出: `awaiting_time_pref` 中の顧客発話ごとに 1 回（小さな構造化抽出）
- いずれも顧客本文が Anthropic へ送られる既存の運用注意の範囲内。1 ターンあたりの追加は**最大 2 回**（`awaiting_time_pref` 中の発話が false 分類 → evaluate → 聞き返し生成、と流れるパス。時間帯返信と分類された発話は evaluate に入らないため 1 回で済む）

## 8. テスト

- `clarification_allowed` の契約テスト（退行防止）: 第 1 層・第 2 層起因の Escalate で false、第 3 層 InsufficientDirectness / UnknownAddedSignal で true
- 応答決定（第 2 節の表）: clarify 条件成立 / clarify_turns=3 で枯渇 / clarification_allowed=false、の分岐を純関数で検証
- 営業時間判定: 時間内 / 時間外（早朝・深夜・週末）/ 境界（10:00 ちょうど・18:00 ちょうど → 10:00 は内、18:00 は外）
- 希望時間帯: 重なりあり / なし（時間外でも 1 回で受け付け、付記付きで保存されること）/ is_time_preference=false で evaluate へ流れること / false 2 連続で awaiting_time_pref が解除されること
- clarify_turns がエスカレーション応答送信でリセットされること
- エスカレーション応答の組み立て: 営業時間内（案内なし）/ 時間外（案内あり）、受付番号の形式
- 聞き返し・受け止め文の egress gate 却下時フォールバック
- 聞き返し・受け止め文の生成上限（max_tokens）による途中切断時のフォールバック
- E2E（デプロイ後、実 LINE）: 曖昧質問 → 聞き返し → 情報追加 → 回答または文脈付きエスカレーション / 時間外希望 → 付記付き受理 / 聞き返し中の「担当者につないで」→ 即エスカレーション

## 9. スコープ外

- 自動の経過連絡（push 通知）
- 固定 SLA 文言・スタッフ空き時間管理（ユーザー判断で不採用）
- 祝日カレンダー
- グレーゾーン（カバレッジ 0.6〜0.8）のハイブリッド応答
- MCP 経路への聞き返し・時間帯フローの適用
