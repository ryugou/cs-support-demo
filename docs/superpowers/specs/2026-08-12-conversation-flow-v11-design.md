# 会話フロー v1.1: ヒアリングループとエスカレーション応答の文脈化

| 項目 | 内容 |
| --- | --- |
| 目的 | `/api/reply` 経路の会話フローを定める: 聞き返しによる情報収集、文脈化されたエスカレーション応答、希望時間帯の受付 |
| 読者 | 実装エージェント、レビュー担当 |
| 正本の範囲 | ヒアリングループの条件と上限、エスカレーション応答の構成、営業時間の判定、希望時間帯の抽出・検証、case への状態追加 |
| 関連文書 | `docs/superpowers/specs/2026-08-11-answer-api-line-adapter-design.md`（`/api/reply` 契約の正本。本書はその応答決定 §4 を置き換える）、GitHub Issue #17 |

## 1. 採用する設計

`/api/reply` の応答決定を「即答 / 即エスカレーション」の 2 値から、「即答 / **聞き返し（最大 3 ターン）** / 文脈化エスカレーション」の 3 値に拡張する。聞き返しで集まった発話は既存の case 機構（signal 累積 → 毎ターン再判定）に乗るため、判定の仕組み自体は変更しない。エスカレーション応答は「受け止め文（生成）+ 決定的ブロック（受付番号・希望時間帯の伺い・営業時間案内）」の合成とし、期限の断定はしない。

適用は `/api/reply` 経路のみ。MCP tool（`evaluate_answerability`）の入出力・挙動は変更しない。

## 2. 応答の決定（v1 design doc §4 の置き換え）

| evaluate の結果 | 応答 |
| --- | --- |
| allowed かつ下書きあり（truncated でない） | `customer_reply_draft` |
| escalate かつ `clarification_allowed = true` かつ case の `clarify_turns < 3` | **聞き返し**（第 3 節） |
| escalate（上記以外）/ rule_match / allowed で下書き null か truncated | **エスカレーション応答**（第 4 節） |

- `clarify_turns` の上限は config `[api] clarify_max_turns`（既定 `3`）
- フォールバック規則（生成失敗・egress 却下時に定型文へ落とす）は v1 と同じ思想で、聞き返し・エスカレーションそれぞれに定型文を持つ（第 3・4 節）

## 3. 聞き返し（ヒアリングループ）

- 生成: LLM に「質問の受け止め + 情報を集めるための確認質問 1〜2 個」だけを書かせる。入力は顧客質問・検索上位ヒットの title・判定の不足情報（不足カバレッジ等）。**回答・手順・仕様の内容を含めることを禁止**するプロンプト制約を置き、egress gate を通す
- 生成失敗・gate 却下時の定型文: 「状況を詳しく教えていただけますか。製品名、いつから発生しているか、画面にエラー表示があるか、が分かると調査が早くなります。」
- 聞き返しを送信するたび、case 属性 `clarify_turns` を +1 して永続化する（第 6 節）
- 次ターンの顧客発話は通常どおり evaluate に入る。signal 累積により allowed へ変われば即答、変わらなければ本節の条件を再評価する
- 3 ターン消費後も escalate のままなら第 4 節へ。それまでに集まった発話・signal は case 経由で担当者に渡る（既存機構のまま）

## 4. エスカレーション応答

応答文 = 受け止め文 + 決定的ブロックの連結。

**受け止め文（LLM 生成、egress gate 経由）**: 「ご質問いただいている○○の件、担当者が確認のうえご連絡いたします」に相当する 1〜2 文。○○は顧客質問からの主題の言い換え。回答内容・期限の約束を含めることを禁止する。生成失敗・gate 却下時の定型文: 「お問い合わせありがとうございます。担当者が確認のうえ、あらためてご連絡いたします。」

**決定的ブロック（コードで組み立て、LLM を通さない）**:

1. 受付番号: 「受付番号: {case_ref}」。`case_ref` は `case_id` の UUID 部分の先頭 8 文字
2. 希望時間帯の伺い: 「ご連絡のご希望時間帯があればお知らせください（対応時間: {営業時間の表記}）。可能な限り合わせます。」送信時に case 属性 `awaiting_time_pref = true` を立てる
3. 営業時間外の受付案内（受付時刻が営業時間外のときのみ）: 「現在は対応時間外のため、担当者からのご連絡は翌営業時間（{営業時間の表記}）以降となります。」

期限の断定（「1 営業日以内」等の固定 SLA 文言）は置かない。

## 5. 希望時間帯の受付

case の `awaiting_time_pref = true` のとき、次の顧客発話を最初に時間帯返信かどうか分類する。

- 分類と抽出: LLM で `{ is_time_preference: bool, windows: [{ days: "weekday" | "weekend" | "any", start: "HH:MM" | null, end: "HH:MM" | null }], raw: string }` を構造化抽出する。「午後」「夕方以降」等の曖昧表現は windows の start/end を常識的な時刻に正規化させる（例: 午後 = 12:00–18:00）
- `is_time_preference = false` の場合: `awaiting_time_pref` は維持したまま、その発話を通常の evaluate フロー（第 2 節）に流す
- `is_time_preference = true` の場合、**営業時間との重なり判定はコードで行う**:
  - 重なりあり: 「承りました。{raw} の時間帯でご連絡できるよう担当者に申し伝えます。」と返し、case 属性 `preferred_contact_time = raw` を保存、`awaiting_time_pref = false`
  - 重なりなし: 「申し訳ありません、その時間帯は対応時間外です。{営業時間の表記}の範囲でご都合の良い時間帯はありますか。」と返し、`awaiting_time_pref` を維持する。この訂正は case 通算 2 回まで。2 回を超えたら `preferred_contact_time = "{raw}（対応時間外の希望）"` として保存し `awaiting_time_pref = false`（担当者が見て判断する）
- 時間帯受付の応答はすべて定型文組み立て（LLM 生成なし）。抽出だけが LLM で、判定・応答はコード

## 6. 営業時間と case 属性

営業時間は config `[api].business_hours`:

| キー | 既定 |
| --- | --- |
| `days` | `"mon-fri"`（`mon-fri` / `everyday` の 2 値） |
| `start` | `"10:00"` |
| `end` | `"18:00"` |
| `tz` | `"Asia/Tokyo"` |

表記文字列は days/start/end から組み立てる（`mon-fri` → 「平日 10:00〜18:00」）。「営業時間内か」の判定は現在時刻（tz 変換後）と start/end の比較のみ。祝日は考慮しない（v1.1 のスコープ外、担当者側の運用で吸収）。

case ノードへ追加する属性（すべて加算のみ・後方互換）:

| 属性 | 型 | 用途 |
| --- | --- | --- |
| `clarify_turns` | int（既定 0） | 聞き返し回数の上限判定 |
| `awaiting_time_pref` | bool（既定 false） | 次発話を時間帯返信として解釈するか |
| `time_pref_corrections` | int（既定 0） | 時間外希望の訂正回数（上限 2） |
| `preferred_contact_time` | string（任意） | 担当者への申し送り |

## 7. LLM 呼び出しの増分（運用注意）

- 聞き返し生成: escalate かつ clarify 条件成立時に 1 回
- 時間帯抽出: `awaiting_time_pref` 中の顧客発話ごとに 1 回（小さな構造化抽出）
- いずれも顧客本文が Anthropic へ送られる既存の運用注意の範囲内。1 ターンあたりの追加は最大 1 回（聞き返し生成と時間帯抽出は同一ターンで両方は発生しない: 時間帯返信と分類された発話は evaluate に入らないため）

## 8. テスト

- 応答決定（第 2 節の表）: clarify 条件成立 / clarify_turns=3 で枯渇 / clarification_allowed=false、の分岐を純関数で検証
- 営業時間判定: 時間内 / 時間外（早朝・深夜・週末）/ 境界（10:00 ちょうど・18:00 ちょうど → 10:00 は内、18:00 は外）
- 希望時間帯: 重なりあり / なし / 訂正 2 回超過 / is_time_preference=false で evaluate へ流れること
- エスカレーション応答の組み立て: 営業時間内（案内なし）/ 時間外（案内あり）、受付番号の形式
- 聞き返し・受け止め文の egress gate 却下時フォールバック
- E2E（デプロイ後、実 LINE）: 曖昧質問 → 聞き返し → 情報追加 → 回答または文脈付きエスカレーション / 時間外希望 → 訂正案内

## 9. スコープ外

- 自動の経過連絡（push 通知）
- 固定 SLA 文言・スタッフ空き時間管理（ユーザー判断で不採用）
- 祝日カレンダー
- グレーゾーン（カバレッジ 0.6〜0.8）のハイブリッド応答
- MCP 経路への聞き返し・時間帯フローの適用
