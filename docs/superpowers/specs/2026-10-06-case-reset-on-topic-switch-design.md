## 1. 採用する設計

切り替えの検知は**サーバ側（`/api/reply`、CS の経路）**で行い、LINE アダプタは応答の指示に従って履歴と case を捨てるだけにする。アダプタに判定を持たせない（アダプタは署名検証・API 呼び出し・LINE への返信だけを行う薄い層、という現行の役割を保つ）。

検知は 2 系統とする。

1. **製品の切り替え（自動）**: その case でこれまでに確定した取扱製品の型番と異なる取扱製品の型番が、今ターンの発話で確定したとき。
2. **利用者による明示（手動）**: LINE のクイックリプライ「別の相談を始める」が押されたとき。アダプタはサーバを呼ばずにセッションを空にする。

切り替えたときは**新しい case を作る**。同一 case のまま履歴だけを切る方式は採らない。理由: case は監査と累積 signal の単位であり、別の相談を同じ case に続けると、古い相談の signal が新しい相談の判定に混ざる。旧 case はそのまま残し、新 case から参照する。

アドバイザー（homesec）の経路では、1 の自動検知を行わない。製品の比較は相談の一部であり、型番が変わることは切り替えではないため。2 の手動のリセットはアダプタの動作なので、アドバイザーの LINE でも同じように効く。

## 2. 製品の切り替えの検知（`/api/reply`、CS の経路）

### 2.1 case が持つ製品の文脈

`support_case` に属性 `product_models` を追加する（加算のみ）。値は、その case のターンで確定した取扱製品の型番の集合を、CSV（型番を辞書順に並べ、`,` 区切り）で持つ。空文字は「まだ確定した型番が無い」を表す。

ターンごとに、`evaluate` が得た `product_references` のうち `resolution == Matched` の `matched_model` を集合に加えて書き戻す（既存の case 属性の read-merge-write と同じ経路）。`Foreign`（取扱外）と `Ambiguous` は加えない。

### 2.2 検知の規則

次をすべて満たすとき、切り替えと判定する。

- リクエストに `case_id` があり、その case の `product_models` が空でない。
- 今ターンの `product_references` に `Matched` が 1 件以上ある。
- 今ターンの `Matched` の型番のいずれも、case の `product_models` に含まれない。

判定は `evaluate` の判定（3 層判定）より前に行う。比較そのものは決定論で、LLM を使わない。比較の入力である今ターンの `product_references` は、case の `product_models` が空でないときだけ、この判定のために抽出する。抽出は signal と製品参照を一体で行い（`evaluate` が内部で行うのと同じ関数）、その結果（signal・抽出モード・生の製品参照）を、切り替えの有無にかかわらず `evaluate` に引数として渡す。`evaluate` は内部で抽出し直さない。1 ターンの抽出は 1 回に保つ。検知を行わないターンは `evaluate` が内部で抽出する。

切り替えの判定は、`evaluate` と同じ採用規則を適用した後の製品参照で行う。signal 抽出が劣化したターン（`Hybrid` 以外）では `evaluate` が製品参照を採用しないため、生の抽出に別の型番が出ていても切り替えは起きない。採用規則は `evaluate` が 1 度だけ適用する（検知側は同じ関数を別のコピーに適用して判定するだけで、`evaluate` へ渡す値は採用前のまま）。

次は切り替えと判定しない。

- 今ターンに `Matched` が無い（型番に触れない発話）。
- 今ターンの `Matched` に、case の `product_models` に含まれる型番が 1 つでもある（既知の製品との比較は同じ相談とみなす）。
- case の `product_models` が空（これまで型番が出ていない）。
- 取扱外の型番だけが出た（二段目ゲートが従来どおり扱う）。

### 2.3 切り替え時の処理

1. 新しい case を作る。`end_user_id` は旧 case の値を継承する（リクエストの値が省略・相違でも旧 case の値を使う。旧 case に値が無いときだけリクエストの値を使う）。属性 `previous_case_id` に旧 case の `case_id` を入れる（加算のみ。新しい属性）。切り替えターンの会話ターン記録の `end_user_id` も同じ値を使う。
2. リクエストの `history` を**使わない**。今ターンは新 case の最初のターンとして、履歴なし・累積 signal なしで判定する（Jev へ渡す履歴も空）。`is_continuation` は初回扱いにする。判定には §2.2 で抽出済みの結果（signal・製品参照）を使い、抽出し直さない。
3. 旧 case の状態は変更しない（取次確定・希望時間帯などの状態は旧 case に残る）。
4. 監査イベントを 1 件記録する。種別は case の切り替え、内容は旧 `case_id`、新 `case_id`、理由（`product_switch`）、旧 case の `product_models`、今ターンの `Matched` の型番。発話本文は記録しない。
5. 応答の `case_id` は新 case のもの、`case_reset` は `true`。

### 2.4 応答フィールド

`ReplyResponse` に `case_reset: bool` を追加する。切り替えが起きたターンだけ `true`。それ以外は `false`。既存の呼び出し側は未知のフィールドを無視する前提で、応答の形の変更はこのフィールドの追加だけとする。

## 3. LINE アダプタ

### 3.1 `case_reset` への追従

応答の `case_reset` が `true` のとき、アダプタはセッションの `history` を空にし、`case_id` を応答の値に置き換える。そのうえで、今ターンの顧客発話と返信を新しい履歴の先頭に積む（既存の「顧客ターン保存 → 返信 → 成功時に assistant ターン追記」の順序は変えない。ただし顧客ターンの保存は `case_reset` の判定後に行えるよう、リクエスト前に積んだ分を捨ててから積み直す）。

`case_reset` が無い（古いサーバ）応答は `false` として扱う。

### 3.2 明示的なリセット（クイックリプライ）

- ボットのすべての返信に、クイックリプライ「別の相談を始める」を 1 件付ける。既にクイックリプライを付けている返信（アドバイザーの選択肢）では、末尾に加える。LINE の上限（13 件）を超える場合は、選択肢側を優先し、この項目を落とす。
- 項目はポストバックアクション（`data=action=reset_case`）とする。テキストアクションにしない（利用者の発話として API に送られてしまうため）。
- アダプタはポストバックイベントを受けたら、`data` が `action=reset_case` のときだけ、セッションを空にし（`case_id` を `None`、`history` を空）、固定の返信文を返す。返信文は環境変数 `CS_LINE_RESET_TEXT` で指定し、既定は「新しいご相談として承ります。内容をお知らせください。」とする。
- 他のポストバックは無視し、warn を 1 行出す（`data` の値は出さない）。

ポストバックはサーバを呼ばないため、サーバ側の case には何も起きない。次の発話が `case_id` なしで送られ、サーバが新 case を作る。

### 3.3 ラベルの表示名

クイックリプライのラベルは環境変数 `CS_LINE_RESET_LABEL` で指定し、既定は「別の相談を始める」とする（20 字以内。LINE の上限に合わせて切り詰めず、超過時は起動時にエラーにする）。

## 4. 不変条件

- 切り替えの判定は決定論で、サーバ側だけが行う。アダプタは判定しない。
- 旧 case の内容・状態は変更しない。監査の記録は追記のみ。
- 切り替えが起きないターンの判定・応答は変更前と同一である。
- アドバイザーの経路では、製品の切り替えによる自動リセットを行わない。
- `product_models` は判定の入力（切り替えの検知）にだけ使い、回答可否の判定には使わない。

## 5. 既知の限界

- 同じ製品について別の事象を相談し始めた場合（例: 設置の話から故障の話へ）は検知しない。累積 signal が増えて取次側に倒れる現行の挙動のまま。利用者はクイックリプライで切り替えられる。
- 型番を一度も出さない相談どうしの切り替えは検知しない。
- 旧 case で型番 A の相談をしている最中に、比較のために型番 B だけを出した発話は切り替えと判定される（A に触れずに B だけを言った場合）。この場合も取次先や判定が誤るわけではなく、新 case として扱われるだけである。
- 取扱外の型番と、取扱内の新しい型番が同じ発話に混在する場合は、切り替えを検知しない。取扱外の型番を含む発話は、質問側の取扱外ゲートが切り替えの検知より前に取扱外応答を返すためである（§2.2 の「取扱外の型番だけが出た」より広く、取扱外が 1 つでもあれば検知に到達しない）。この発話の取扱外応答は旧 case に記録される。次の発話で取扱内の型番だけを出せば、そのターンで切り替えが検知される。製品参照の扱いを見直す Issue #57 で、取扱外ゲートと切り替え検知の順序も合わせて扱う。
- 切り替えの検知を行うターン（`case_id` があり `product_models` が空でない）では、signal と製品参照の抽出を `evaluate()` の前に行う。`evaluate()` の中では抽出と他の読み出し（KnownResolution 等）を並列に行っていたため、このターンに限り、抽出の所要時間がそのまま応答時間に加わる。LLM の呼び出し回数は変わらない（1 ターン 1 回）。この影響は Issue #85（処理ごとの所要時間の記録）で実測し、Issue #86（抽出と読み出しの並列化）で扱う。

## 6. テスト

| 対象 | 固定する内容 |
| --- | --- |
| 検知の規則（純関数） | 2.2 の条件を満たす組み合わせで切り替え、満たさない 4 つの場合で非切り替え |
| `product_models` の更新 | `Matched` だけが加わり、`Foreign` / `Ambiguous` は加わらない。辞書順 CSV で書き戻される |
| 切り替え時の処理 | 今ターンが履歴なし・累積 signal なしで判定される。旧 case の状態が変わらない。監査イベントが 1 件記録され、発話本文を含まない |
| `end_user_id` の継承（純関数） | 切り替えターンは、リクエストで省略されても旧 case の値を使う。リクエストの値が旧 case と異なっても旧 case の値を使う。旧 case に値が無い（空を含む）ときはリクエストの値を使う。切り替えでないターンはリクエストの値のまま |
| 採用規則と切り替え判定（純関数） | signal 抽出が `LexiconFallback` / `LexiconOnly` のターンは、生の抽出に別の型番が `Matched` で出ていても切り替えない。`Hybrid` のターンは従来どおり切り替える。どちらも抽出結果（抽出モード・生の参照）を `evaluate` へ持ち回る |
| 抽出の回数 | `evaluate` に抽出済みの結果（signal・抽出モード・製品参照）を渡すと、signal 抽出と製品参照抽出の LLM 呼び出しがどちらも 0 回で、渡した値がそのまま使われる。渡さない（`None`）と内部で各 1 回抽出する。検知の判定は、切り替えの有無にかかわらず抽出結果を `evaluate` へ持ち回る。case 属性の読み込み失敗時は抽出結果なし（`None`）になる |
| 応答 | 切り替えターンだけ `case_reset: true`。それ以外は `false`。既存の応答テストが `case_reset` の追加以外で変わらない |
| アドバイザー | 型番が変わっても `case_reset` が `false` のまま |
| アダプタ: `case_reset` | `true` の応答で履歴が空になり、新 `case_id` に置き換わり、今ターンだけが履歴に残る。`false` と欠落は従来どおり |
| アダプタ: ポストバック | `action=reset_case` でセッションが空になり固定文を返す。他の `data` は無視して warn。サーバを呼ばない |
| アダプタ: クイックリプライ | 返信にポストバックの項目が付く。選択肢と合わせて 13 件を超えるときは項目が落ちる。ラベルの長さ超過は起動時エラー |

## 8. 対象外

- 相談対象の切り替えを LLM で判定すること。
- 事象の切り替え（同じ製品で別の相談）の自動検知。
- セッションの永続化（別の段階で扱う）。
