# CS 応答システム 処理フローと設計概念

| 項目 | 内容 |
| --- | --- |
| 目的 | 本システムが AI エージェントとして 1 通のメッセージにどれだけ細かな意思決定を重ねているか(オーケストレーション)を、「この記述どおりに図にすればフローチャートが描ける」粒度で示し、あわせて特有の設計概念(目的・考え方・導入理由)を説明する。チャネル(LINE 等)の配管は対象外 |
| 読者 | 本システムを初めて理解する開発者・レビュー担当・関係者 |
| 位置づけ | 本書単体で読める自己完結の説明文書。実装の契約・正確な閾値・文言の正本はコードと各仕様書にあり、本書は挙動の説明を優先する |

## 第 1 部: 処理フロー

### 1. エージェントの応答オーケストレーション — 1 メッセージの意思決定パイプライン

顧客メッセージ 1 通(+ 会話履歴 + 会話 ID)を受け取ってから応答文を確定するまでに、エージェントは以下の 7 フェーズを通る。**LLM を呼ぶのは最大 3 箇所**(理解・下書き生成・聞き返し/受け止め文生成)で、**それ以外の分岐・裁定・関門はすべて決定論のコード**が行う。

**フェーズ A: 入口の決定論ゲート(LLM を使わずに終わる経路)**

- A1.【取扱スコープ・一段目】メッセージを正規化(全角・各種ハイフン・不可視文字)して正規形の型番を検出し、取扱外型番があるか判定する
  - あり → 取扱外定型応答(自社取扱一覧 + 購入元への案内)を組み立ててフェーズ G へ直行。**以降の全工程をスキップし、LLM コストはゼロ**
- A2.【時間帯受付モード】この会話が「希望時間帯を伺い中」ならフェーズ B へ、そうでなければフェーズ C へ

**フェーズ B: 時間帯の解釈と受付(解釈は LLM、判定はコード)**

- B1. メッセージが時間帯の返答かどうかを LLM で構造化抽出する(曖昧表現「夕方以降」も時刻範囲へ正規化)
- B2. 時間帯だった → 営業時間(設定値。既定は平日 10:00〜18:00)との重なりを**コードで**計算し、受付文(時間外なら「ご希望に添えない場合があります」の但し書き付き)を組み立ててフェーズ G へ。時間帯でなかった → 誤分類カウンタを進めてフェーズ C へ合流(2 回連続で伺いモードを自動解除。LLM 障害は別カウンタで 3 回まで許容 — 一時障害で顧客の回答を取りこぼさないため)

**フェーズ C: 理解 — 発話の構造化(LLM 呼び出し 1 回に相乗り)**

- C1. 発話を統制語彙(signal)へ正規化する(LLM + 語彙辞書のハイブリッド)
- C2. 同じ呼び出しで製品参照も解釈する(取扱カタログを注入し、matched / ambiguous / foreign の三値で分類)
- C3. LLM 障害で語彙辞書のみに劣化したターンには劣化フラグを立てる(フェーズ F で fail-closed に使う)

**フェーズ D: 文脈復元と三層判定**

- D1. 会話(case)をロードし、**過去ターンの累積 signal と今ターンを合流**させる(判定は常に会話全体で行う)
- D2. 文書グラフから材料を検索する。**取扱外製品だけに言及する記事は判定より前に材料から除外**(型番言及のない汎用記事は残す)
- D3. 三層で判定する: 第一層 = 人間が書いた明示エスカレーションルール(「担当者につないで」の取次依頼もここ)→ escalate 確定 / 第二層 = 禁止ドメイン → escalate 確定 / 第三層 = 材料カバレッジの閾値判定 → 未達なら escalate(**この層だけ「聞き返し許可」がつき得る**)、達すれば allowed。検証済みノウハウ(known_resolution)の適用条件照合も判定に組み込まれる
- D4. allowed なら回答下書きを生成する(材料 + 会話履歴を注入 → NG 語ゲート → 生成途中切断の検査)

**フェーズ E: スコープ裁定・二段目(LLM の解釈を検証してから採用する)**

- E1. フェーズ C の製品参照に「カタログ外と確信できる参照(foreign)」があれば、採用前に 3 つの検証を通す: 幻覚ガード(その表層文字列が実際にメッセージ中に存在するか)/ 取扱内 veto(表層・対応型番のどちらかが自社製品を指していないか。型番断片のサフィックス照合込み)/ 反射安全性(応答へそのまま載せて安全な文字列か)
  - 全通過 → 取扱外定型応答へ差し替え、**会話の正本も「取扱外で断った」に修正**(生成済み下書きは破棄。破棄ターンの signal は累積から除外しつつ、後で再観測されたら復帰する非永久管理)→ フェーズ G へ

**フェーズ F: 応答の選択(三値)と会話設計**

- F1. 劣化フラグ(C3)が立っていれば、判定結果によらずエスカレーション応答(fail-closed。抽出 LLM が不調なら生成 LLM も不調で、どのみち自動回答は成立しないため実質コストなし)
- F2. allowed + 健全な下書き → **回答**。継続会話なら挨拶オープナーを抑止し、締めは「解決しそうか」を問う継続誘導の一文にする(会話終了風の定型句は禁止)
- F3. escalate + 聞き返し許可 + 残り回数あり → **聞き返し**を生成: 把握済み事項リスト(累積 signal + 直近発話の要点)を渡して再質問を禁止し「〜とのことですね」と受け止めさせる / 質問数は短答・選択式のみ最大 2 問(部分回答歓迎の文言付き)・記述式は 1 問 / 上限到達の回だけ「この確認で最後です」をコードで付す(最大 3 ターン)
- F4. それ以外 → **エスカレーション応答**: 受け止め文(LLM、件名の言い換えのみ・回答や期限の約束は禁止)+ 決定的ブロック(受付番号 / 希望時間帯の伺い / 営業時間外ならその案内)。「時間帯を伺い中」モードを起動し、聞き返し予算をリセットする

**フェーズ G: 出口の関門と記録(生成物は無検査で顧客に届かない)**

- G1.【応答側スコープゲート】生成由来の応答文に取扱外型番の言及があれば**応答ごと破棄**してフォールバック定型文へ
- G2.【プレーンテキスト正規化】Markdown 記法・不可視文字をコードで除去する
- G3.【記録】質問・確定応答文・応答種別・監査 ID を会話ターンとして永続化(5 秒上限。失敗しても応答を優先)→ 応答文を返却

**まとめ(粒度の要約)**: 1 通の応答までに、決定論ゲート 4 つ(入口スコープ / fail-closed / 出口スコープ / プレーンテキスト)、LLM と決定論の役割分離が 2 箇所(時間帯・製品参照)、会話状態の管理が 5 種(累積 signal / 聞き返し残数 / 時間帯モード / 誤分類・障害カウンタ / 除外 signal の非永久管理)が働く。応答の種類は 6 つ(回答 / 聞き返し / エスカレーション / 取扱外 / 時間帯受付 / フォールバック)で、どれになったかは監査 ID で追跡できる。

### 2. サブフロー — ヒアリングループ(聞き返しの反復)

1. 曖昧な質問 → 三層判定で「カバレッジ不足(第三層)」→ 聞き返し(メインフロー 11)
2. 顧客が答える(部分回答でもよい)→ 次ターンの signal 抽出で**判定材料が増える**
3. 累積 signal で毎ターン再判定する
   - カバレッジが閾値を超えた → 回答へ切り替わる
   - 超えないまま 3 ターン消費 → 集めた情報付きでエスカレーション応答へ
4. 途中で顧客が「担当者につないで」と言えば、第一層の明示ルールが拾い、残回数に関係なく即エスカレーション
5. 会話の区切り: 挨拶の出し分け(初回のみ挨拶、継続は本題から)はコードが判定した会話段階フラグで制御する。会話セッションの寿命はチャネル側の管理(現行は 60 分無応答で新規会話扱い)

### 3. サブフロー — CS 担当のノウハウ蓄積ループ(MCP 経由)

1. エスカレーションされた問い合わせを CS 担当(人間)が確認する(claude.ai の MCP コネクタ経由)
2. 担当者が正しい答えを決める(例:「MFA は非対応」という否定事実など、マニュアルに書かれていないこと)
3. `add_known_resolution` で「適用条件(signal 集合 + 適用範囲の記述)+ 検証済み回答」を登録する
4. 以後、同じ条件に合致する質問は known_resolution が判定で優先され、登録済みの回答で即答できる
5. 回答は登録・撤回とも離散的(1 件単位)で、監査ログに残る

### 4. 運用フロー — データ構築(全体リセット時)

1. 製品マスタ投入(`ingest-products`)— 以降の工程とスコープ判定の正本
2. マニュアル取り込み(`ingest-urtect` = 自社マニュアル / `ingest-alarmcom` = alarm.com KB 全記事。順不同・並行可)+ ルール投入(`ingest-rules`)
3. コミュニティ構築(`merge-schema` = グラフ全体の再計算。global 検索の前提)
4. 概念キー射影(`backfill-concept-keys`。差分取り込み時のみ必要)
5. 検索品質の測定(`verify-alarmcom` で recall / MRR / 誤ヒット率)
6. コード変更の本番反映は main マージ → CI のみ(手動デプロイ禁止)

## 第 2 部: この仕組み特有の設計概念

### 2.1 Punk Record(vegapunk)と「材料と判定の分離」

- **何か**: vegapunk(Punk Record)は、文書グラフ・製品マスタ・会話 case・ノウハウを格納・検索する基盤。本システムはそこに**材料だけ**を置き、**判定・強制・ゲートはすべて製品側(cs-support-mcp)**で行う。
- **考え方**: 基盤は「事実の置き場と検索」に徹する。スキーマ変更は加算のみ(後方互換を壊さない)。「答えてよいか」「何を答えるか」「何を顧客に出すか」という判断のロジックは 1 か所(製品側)に集約する。
- **なぜ**: 判定を基盤側に埋めると、判定の変更・監査・fail-closed 制御が基盤の都合に縛られる。分離しておけば、基盤障害時に製品側が安全側(エスカレーション)へ倒す設計が貫け、判定ロジックの進化(ゲート追加など)が基盤に触れずに済む。

### 2.2 文書グラフと構造 traversal(grep しない検索)

- **何か**: マニュアルを「文書 → 節 → 子節」の木構造 + 参照辺 + 概念辺としてグラフに保持し、検索ヒットから祖先・子・参照先を辿って根拠を組み立てる。英語原文を正本、日本語を投影として持ち、原文変更をハッシュで検知して stale を管理する。
- **なぜ**: 平文 grep では「どの製品のどの手順の一部か」という文脈が失われ、根拠の追跡(この回答はどの節に基づくか)ができない。構造を持てば、回答の出典を節単位で示し、翻訳の鮮度も節単位で管理できる。

### 2.3 三層判定と fail-closed(答えないと決めたら答えない)

- **何か**: 回答可否を「第一層: 人間が書いた明示ルール → 第二層: 禁止ドメイン → 第三層: 材料カバレッジの閾値」の順で判定する。上位層ほど強く、上位でエスカレーションが確定したら下位は見ない。障害・不確実性は常にエスカレーション側へ倒す(fail-closed)。
- **なぜ**: CS の信頼の核は「確実なエスカレーション」— 危ない・分からない案件が確実に人間へ届くこと。LLM の判断力に頼った1 段判定だと「もっともらしく答えてしまう」事故を構造的に防げない。決定論の層を上に置くことで、「規制対象は必ず人間」のような約束を仕様として保証できる。

### 2.4 signal 語彙と会話層の累積(聞き返しが意味を持つ理由)

- **何か**: 顧客の発話を統制語彙(signal)へ正規化して case に蓄積し、**毎ターン、累積全体で再判定**する。
- **考え方**: 会話とは判定材料が増えていく過程である。「変色した」だけなら様子見でも、次のターンで「カビも生えた」が加われば、累積(変色 + カビ)での再判定が自動的にエスカレーションへ倒れる。
- **なぜ**: 聞き返し(ヒアリング)を「材料集め」として判定系に接続するため。文面の印象ではなく語彙化された条件の集合で判定するので、挙動が説明可能・監査可能になり、known_resolution の適用条件にも同じ語彙が使える。

### 2.5 known_resolution — ノウハウの離散進化(GMR)

- **何か**: 担当者が検証した「この条件ならこの答え」を、1 件単位の例外ルールとして登録する仕組み。マニュアルに無い知識(否定事実・現場判断)をここに貯める。
- **考え方**: モデルの再学習や文書の書き換えではなく、**離散 insert** で知識を進化させる。適用条件は人間が明示し(LLM に推測させない)、登録・撤回が個別にでき、全件が監査に残る。
- **なぜ**: CS の学習は「昨日の誤答を今日直せる」ことに価値がある。再学習は遅く、効果が不透明で、巻き戻せない。離散ルールなら即日反映・効果が確定的・撤回可能で、「誰がいつ何を教えたか」を説明できる。

### 2.6 egress gate — 顧客到達面の決定論保証

- **何か**: LLM が生成した文は、顧客に届く前に必ずコードの関門を通る: NG 語検査 / 生成途中切断(truncated)の破棄 / 取扱外型番の検出 / プレーンテキスト正規化。関門で落ちたら定型文へフォールバックする。
- **なぜ**: プロンプトによる指示は確率的で、「絶対に出してはいけないもの」の保証にはならない。禁止・破棄・正規化という決定論の出口を 1 か所に置くことで、モデルがどう振る舞っても顧客到達面の下限品質が保証される。「LLM は提案し、コードが許可する」構図。

### 2.7 「解釈は LLM、判定はコード」

- **何か**: 曖昧な自然言語の**解釈**(「夕方以降にして」→ 時間帯、「521IR」→ 製品参照)は LLM の構造化抽出に任せ、**発火の判断**(営業時間内か、取扱外か)は検証付きのコードが行う。LLM の出力には幻覚ガード(実在検証)や、製品マスタと矛盾する分類への veto を掛ける。
- **なぜ**: 顧客入力は表記が当てにならず、正規表現の網では原理的に拾いきれない。一方で LLM に判断まで任せると誤爆を制御・監査できない。解釈と判断を分離すると、LLM の柔軟さと決定論の説明可能性を両取りできる。

### 2.8 取扱スコープの前提化(フィルタではなく世界観)

- **何か**: 「当社が扱う製品(製品マスタが正本)以外には答えない」を、検出して弾くフィルタではなく、**会話全体の前提**として全工程に注入する: 質問側ゲート(二段)・材料選別・聞き返しの選択肢・回答生成の制約・応答側ゲート。
- **なぜ**: マニュアルコーパスには全製品の記事がある(共通手順が有用なため)が、検索は「質問に合う記事」を返すだけで「当社が扱うか」を知らない。スコープの概念をシステムのどこも持たないままだと、聞き返しの選択肢に扱っていない製品種別が出る・他社製品を自社製品として答える、という会話全体の破綻が起きる。型番の明示がない質問(「ドアベルの設定は?」)まで含めて塞ぐには、前提としての注入が必要。

### 2.9 監査の貫通と「正本は顧客に返した事実と一致する」

- **何か**: すべての判定・応答に監査 ID(audit_event_id)が発番され、WORM(追記のみ)ログと case の正本属性に記録される。途中で応答が差し替わった場合(例: 二段目ゲートで取扱外に確定)は、**case の正本も「実際に顧客へ返した内容」に一致するよう修正**する。
- **なぜ**: 「なぜこの応答になったのか」に答えられることが、無人応答を業務に載せる条件。集計(何件断ったか・何件答えたか)が正本とずれていると、運用判断も学習(訂正)も誤る。

### 2.10 デプロイの単一経路(main = 本番)

- **何か**: 本番反映は「PR → レビュー → main マージ → CI が全サービス・全ジョブを同一イメージタグへ更新」の一本のみ。手動デプロイは禁止。
- **なぜ**: 本番で動くコードの出自が main で保証されないと、障害調査も再現も監査もできない(実際に「本番のコードが main に無い」状態が事故として発生し、恒久ルール化した)。
